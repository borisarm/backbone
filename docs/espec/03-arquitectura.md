## 3. Arquitectura

```
┌───────────────────────────────┐                 ┌─────────────────────────────────────┐
│ Backbone.App (WinUI 3)        │                 │ Backbone.Service (Worker, .NET 10)  │
│ sesión del usuario            │  named pipe     │ sesión 0, LocalSystem               │
│ · icono en bandeja            │  JSON-RPC       │ · Scheduler                         │
│ · panel / trabajos / restaurar│◄──────────────► │ · JobRunner → Backbone.Core         │
│ · historial / ajustes         │  (eventos push) │ · IPC server (ACL)                  │
│ · notificaciones toast        │                 │ · OS: VSS, SMB, DPAPI, EventLog,    │
└───────────────────────────────┘                 │   energía, red                      │
                                                  │ · Almacén: config JSON + SQLite     │
                                                  └──────────────────┬──────────────────┘
                                                                     │ SMB (WNetAddConnection2)
                                                                     ▼
                                                    \\NAS\Backups\<trabajo>\  (repositorio §6)
```

El servicio hace todo el trabajo. La app solo es una interfaz: si se cierra, las copias continúan. Un servicio en la sesión 0 no puede mostrar interfaz, de ahí la separación.

### 3.1 Solución

```
Backbone.slnx
├── src/
│   ├── Backbone.Contracts/   net10.0          DTO, interfaz IPC, códigos de error. Sin dependencias de Windows.
│   ├── Backbone.Core/        net10.0          Motor: repositorio, backup, restore, retención, prune, check, exclusiones, programación.
│   ├── Backbone.Service/     net10.0-windows  Host del servicio, scheduler, servidor IPC, integración con el SO, persistencia.
│   └── Backbone.App/         net10.0-windows10.0.22621.0  WinUI 3 sin empaquetar (WindowsPackageType=None).
├── installer/
│   └── Backbone.Installer/   WiX v5 (MSI)
├── tests/
│   ├── Backbone.Core.Tests/          xUnit, sin red ni privilegios
│   ├── Backbone.Service.Tests/       xUnit, scheduler e IPC con dobles de prueba
│   ├── Backbone.App.Tests/           xUnit, view models y cliente IPC (sin UI real)
│   ├── Backbone.Architecture.Tests/  reglas de dependencia entre proyectos
│   ├── Backbone.Contracts.Tests/     contrato IPC: ida y vuelta de cada DTO, convenciones, errores y eventos con StreamJsonRpc en memoria
│   └── Backbone.IntegrationTests/    requieren admin / recurso SMB local; marcados con [Trait("Category","Integration")]
└── docs/
```

Reglas de dependencia: `App → Contracts`; `Service → Core → Contracts`. **La app nunca referencia Core ni Service.** Core no conoce Windows (salvo `System.IO`): todo lo específico del SO vive en Service detrás de interfaces. `Backbone.Architecture.Tests` comprueba estas reglas leyendo los `.csproj` de `src/` (cierre transitivo de `ProjectReference`) y, para Contracts y Core, también las referencias de los ensamblados compilados.

Compilación: SDK fijado en `global.json` (10.0.x); propiedades comunes en `Directory.Build.props` y versiones de NuGet en `Directory.Packages.props`. La app, al ser autocontenida, necesita una arquitectura concreta: con `-p:Platform=x64|ARM64` (o `-r win-x64|win-arm64`) se compila para esa arquitectura y, si no se indica, para la de la máquina, de modo que `dotnet build Backbone.slnx` funciona sin opciones.

La llamada directa usa los mismos indicadores que `ProtectedData` por dentro, evita el paquete NuGet `System.Security.Cryptography.ProtectedData` y permite poner a cero el texto en claro que devuelve el sistema antes de liberarlo con `LocalFree`. | ADR-11 | El contenido del repositorio es **no confiable**: límites explícitos de tamaño, número y profundidad en los manifiestos (§6.3), ningún punto de reanálisis dentro del repositorio (→ corrupto), almacenamiento solo sobre destinos UNC que no sean el propio equipo (§6.1) y textos saneados antes de registrarlos o mostrarlos (también toda la categoría Unicode `Cf`, y también en el servicio y la app, con `UntrustedText` de Contracts). Los nombres no direccionables de `locks\` cuentan como bloqueo exclusivo ilegible (latido = fecha de modificación; dejan de bloquear al quedar abandonados) y los de `tmp\` se ignoran; Backbone no los borra (R8). Un latido en el futuro más allá de la tolerancia de reloj es anómalo y no alarga el bloqueo (§6.4.4). El escritor recorta los avisos (`WarningsTruncated`) para no publicar nunca un manifiesto que el lector rechace. | Otro equipo o cualquiera con escritura en el recurso del NAS puede manipularlo; un manifiesto hostil no debe agotar memoria ni registros, ni un *junction* llevar escrituras o borrados fuera del repositorio. Límites holgados (5 000 000 de entradas = 10 × RNF-05) para no rechazar copias legítimas. |
| ADR-12 | La app verifica el servidor del pipe (§7.1 A-1) comparando el PID de `GetNamedPipeServerProcessId` con el del servicio `BackboneService` en el SCM (`QueryServiceStatusEx`, en ejecución, `SERVICE_WIN32_OWN_PROCESS`) y la cuenta configurada del servicio (`QueryServiceConfig`, `LocalSystem`), en lugar de leer el SID `S-1-5-18` del token del proceso servidor. Como defensa en profundidad comprueba además que el propietario del pipe es SYSTEM o Administradores, que el servidor está en la sesión 0 y que el PID no cambia durante la verificación. | Una app sin elevar no puede abrir el token de un proceso SYSTEM; la configuración del SCM es legible por usuarios autenticados y solo un administrador puede cambiarla. Decisión del usuario en HT-03. |
| ADR-13 | La carpeta de datos `%ProgramData%\Backbone` (RNF-07) **nunca se corrige en el sitio si su propietario no es fiable** (ni SYSTEM ni Administradores) o no se puede abrir: se aparta renombrándola a `Backbone.untrusted-<guid>` y se crea una nueva con `CreateDirectoryW` y el descriptor definitivo. Si no se puede apartar, el servicio no arranca. Lo mismo hace el instalador (HU-01 I-1). Si el propietario es fiable, la DACL se corrige en el sitio (riesgo aceptado R9, §13). *Posible mejora*: hoy una raíz `Backbone` que sea *junction* o archivo creada antes de la instalación se **rechaza** (el servicio no arranca y el MSI falla) en lugar de apartarse; podría apartarse por handle igual que una carpeta de propietario no fiable, sin seguir el enlace (revisión de HT-03, I-2). | Quien creó la carpeta puede conservar handles abiertos con `WRITE_DAC` o `FILE_ADD_FILE`, o sustituirla entre la comprobación y la corrección; tomar la propiedad no revoca esos handles. Apartarla no borra nada y deja el contenido para que lo revise un administrador. Decisión de HT-03. |
| ADR-14 | Los almacenes del servicio abren cada archivo de la carpeta de datos por handle sin seguir puntos de reanálisis y lo rechazan si no es propiedad de SYSTEM o Administradores, es un punto de reanálisis o tiene más de un nombre (enlace duro), comprobándolo sobre el mismo handle con el que leen; la escritura atómica crea el temporal con descriptor explícito (§8.2). Los almacenes no crean carpetas: abren la carpeta padre por handle sin seguir puntos de reanálisis y sin `FILE_SHARE_DELETE`, comprueban que es una carpeta de propietario fiable y la mantienen abierta durante la operación; si falta, la operación falla. Las subcarpetas fijas (`config\`, `credentials\`, `data\`, `logs\`) las crea solo el servicio al arrancar, por handle y con herencia de la raíz (§8.3). Si `settings.json` o `jobs.json` se rechaza en el arranque, el servicio no arranca (1002); si se rechaza al escribir después, no se escribe nada y la operación falla (`jobs.json`, decisión del coordinador en HU-07). La comprobación de la carpeta (§8.3) acepta en el contenido tanto la herencia sin ACE explícitas como la DACL protegida canónica con que se crean estos archivos, para no "corregirlos" en cada arranque. | Cierra la ventana entre la comprobación de la carpeta (§8.3) y la lectura de la configuración: lo que un usuario cree con un handle conservado tiene a ese usuario como propietario y se rechaza al leerlo. Que los almacenes no creen carpetas y no sigan la carpeta padre impide que una subcarpeta fija creada de antemano como *junction* lleve escrituras de SYSTEM fuera de la carpeta de datos (revisión final de HT-03). Reduce R9. Decisión del usuario en HT-03. |
| ADR-15 | Se mantiene el nombre de pipe `\\.\pipe\Backbone.Service.v1` (§7.1) y no se usa el prefijo `ProtectedPrefix\Administrators\`. | El prefijo no figura en la documentación de Microsoft ([Pipe Names](https://learn.microsoft.com/windows/win32/ipc/pipe-names)) y no se puede depender de un comportamiento no documentado. El riesgo de ocupación del nombre se acepta (R10, §13). Decisión del usuario en HT-03. |
| ADR-16 | La carpeta de datos `%ProgramData%\Backbone` **nunca se copia al NAS**, con dos capas (§8.3): la validación rechaza un origen que sea esa carpeta o esté dentro de ella (RF-03, `SourceNotAllowed`), y el motor la excluye siempre, como exclusión obligatoria que no se puede quitar, cuando un origen la contiene (RF-04). La exclusión se indica con un aviso de validación (`SourceContainsDataFolder`), que la app muestra como nota fija en la vista de exclusiones, y no como aviso de ejecución. Las dos capas cubren también las carpetas apartadas `%ProgramData%\Backbone.untrusted-<guid>` (ADR-13), que se reconocen por su **ubicación** (`<ruta final de %ProgramData%>\<nombre>`) y solo si son **carpetas reales**: una entrada con ese nombre que sea punto de reanálisis o archivo se ignora y nunca se sigue. Como mucho 100; si hay más, los orígenes que contienen `%ProgramData%` fallan cerrados (`SourceNotAllowed`, `ValidationFailed`) en lugar de recortar la lista. Si no se obtiene la ruta `VOLUME_NAME_GUID` de `%ProgramData%`, fallan cerrados **todos** los orígenes con `ProtectedFoldersUnavailable` (cierre de HU-08 servicio, decisión del coordinador; código propio por decisión del usuario, R16). Códigos en los contratos 1.2 y 1.4. | Con DPAPI de ámbito equipo y entropía que figura en el código fuente (ADR-07), la única protección de `credentials\*.bin` es la ACL local. El servicio lee como SYSTEM y desde VSS, así que con un origen `C:\` subiría esos archivos al NAS, y cualquier usuario local con lectura en el recurso podría descifrarlos en ese equipo. Una carpeta apartada puede contener credenciales antiguas cifradas igual. Un aviso de ejecución convertiría toda copia de `C:\` en "con avisos" para siempre (RF-25); la restauración ya protege la carpeta (§8.6.4). Decidido en la revisión de seguridad de HU-04 (MEDIA-1); las carpetas apartadas, decisión del coordinador en HU-13. `%ProgramData%` deja crear entradas a cualquier usuario: si una carpeta apartada se reconociera por el nombre y se siguiera, un *junction* `Backbone.untrusted-x` sacaría de la copia cualquier carpeta sin aviso, y recortar la lista dejaría fuera una carpeta apartada real (revisión de seguridad final de HU-13, M-B). |
| ADR-18 | La lectura de los orígenes (`ISourceFileSystem`, §8.2) abre **cada elemento relativo al handle de su carpeta padre** (`NtCreateFile` con `RootDirectory`, un solo componente, `FILE_OPEN_REPARSE_POINT \| FILE_OPEN_FOR_BACKUP_INTENT`), en vivo y en VSS, manteniendo abiertos los handles de las carpetas en recorrido (caché acotada, §8.2 "Apertura relativa"); la raíz se abre con la resolución controlada de ADR-20. Nunca se abre un elemento por su ruta completa. Además, como defensa en profundidad, comprueba sobre el mismo handle con `GetFinalPathNameByHandle` que la ruta final es **exactamente** la ruta final de la raíz del origen más la ruta relativa del elemento y que no cae en una carpeta protegida; si no, `SourceAccessException(ReparsePointSkipped)`. La apertura relativa era antes una "alternativa válida"; pasa a ser **obligatoria** (revisión de seguridad del `SourceFileSystem` de HU-08, A-1, decisión del coordinador). La firma de `ISourceFileSystem` no cambia: la implementación se crea por ejecución con los orígenes y deduce la ruta relativa. Si no se puede recorrer la raíz de un origen, el aviso es `SourceRootUnreadable` (contrato 1.2). La raíz de cada origen se obtiene antes con la resolución controlada de ADR-20; en vivo, `SourceFileSystem` no recibe su handle, sino que vuelve a bajar desde el volumen hasta la ruta final de la resolución sin seguir ningún enlace (un enlace nuevo da `SourceRootUnreadable`; cierre de HU-08 servicio, decisión del coordinador). | `FILE_FLAG_OPEN_REPARSE_POINT` solo protege el último componente: en una copia en vivo un usuario puede sustituir una carpeta intermedia ya enumerada por un *junction* y SYSTEM leería `credentials\` (revisión de seguridad final de HU-13, M-A). La comprobación de la ruta final llega tarde para otro efecto: si la carpeta intermedia pasa a ser un *junction* hacia `\RPC Control` con un enlace del administrador de objetos hacia `\??\UNC\atacante\x` (en el momento justo, ayudándose de un oplock), la apertura por ruta completa hace que SYSTEM se autentique con NTLM ante el atacante antes de que se pueda comprobar nada; es el vector de ADR-20 (revisión del `SourceFileSystem` de HU-08, A-1). Con un solo componente relativo a un handle ya abierto no queda ningún componente intermedio que el sistema resuelva por nombre. Pasar la ruta relativa en la interfaz obligaría a cambiar el motor y sus simuladores sin ganar seguridad, porque la implementación ya compone las rutas. Un origen entero sin actualizar no debe confundirse con un archivo suelto ilegible (B-1, R11). |
| ADR-17 | **Snapshot padre** de una copia (§6.3 "Snapshot padre"): el último snapshot del mismo trabajo cuya fecha no supere el inicio de la copia más la tolerancia de reloj (15 min). Si ese padre, o cualquier cabecera que haya que leer para elegirlo, está dañado, la copia **falla** con `Corrupt` (`RepositoryCorrupt`) y no publica nada hasta que el repositorio se verifique o repare (HU-29); no se salta con un aviso. Una copia que supera los límites del manifiesto falla con su propio código, `SnapshotTooLarge` (contrato 1.2). | Con un padre ilegible el motor no sabe qué versión conservar de los archivos que no puede leer (RF-25) y saltarlo cambiaría en silencio a otro padre más antiguo; una cabecera ilegible no se puede descartar como ajena al trabajo. Un snapshot con fecha futura, plantado o de un equipo con el reloj adelantado, no debe quedar como padre de todas las copias siguientes (revisión de seguridad de HU-13, BAJA-4). `SnapshotTooLarge` tiene código propio porque la solución (dividir el trabajo) es distinta de la de cualquier otro fallo. Decisión del usuario en HU-13. |
| ADR-19 | **Puntos de reanálisis por etiqueta, con lista blanca** (RF-06, §8.2 "Clasificación por etiqueta"). Solo es un **enlace** (se omite con `ReparsePointSkipped`, sin seguirlo ni conservar nada) un punto de reanálisis cuya etiqueta es **sustituto de nombre** (`IsReparseTagNameSurrogate`: *junction*, enlace simbólico, punto de montaje). Se leen **por su contenido** solo los elementos sin punto de reanálisis y los de las etiquetas de la lista blanca: `IO_REPARSE_TAG_CLOUD*` totalmente descargado, `IO_REPARSE_TAG_WOF` e `IO_REPARSE_TAG_DEDUP`. **Cualquier otra etiqueta** (ProjFS, proveedores de terceros, HSM desconocidos) es **no legible**: se omite con aviso conservando la versión del snapshot padre (RF-25). Los archivos de OneDrive no descargados, y los que pasan a estarlo, se omiten sin abrirlos con `CloudOnlySkipped` y conservan la versión del padre (RF-06, R4). La etiqueta se lee sobre el handle (`FileAttributeTagInfo`) y en la enumeración, y viaja al motor en `SourceEntry.ReparseTag`. Se mantienen `FILE_FLAG_OPEN_REPARSE_POINT` en la primera apertura y la comprobación de ruta final de ADR-18. El contenido de un elemento de la lista blanca se lee de un **segundo handle sin esa marca**, comprobado sobre él mismo. El servicio expone los marcadores al arrancar (`RtlSetProcessPlaceholderCompatibilityMode(PHCM_EXPOSE_PLACEHOLDERS)`) y toda lectura de los orígenes tiene un plazo por operación (60 s), con un presupuesto de plazos por origen y un tope de hilos abandonados en el servicio (§8.2 "Plazo de las lecturas de los orígenes"). | `FILE_FLAG_OPEN_REPARSE_POINT` desactiva el procesamiento normal: el filtro propietario de la etiqueta puede no intervenir, y la documentación no garantiza que se lea el contenido real. Con Dedup se leería el *stub*; con un marcador de nube, ceros donde no hay datos. Omitir todo punto de reanálisis dejaría fuera los archivos de OneDrive ya descargados, que son reales y del usuario. Seguir cualquier etiqueta desconocida permitiría a cualquier usuario registrar su propia raíz de sincronización (`CfRegisterSyncRoot`) o de ProjFS dentro de un origen y colgar o manipular las lecturas que hace SYSTEM. Los marcadores no descargados se omiten para no desencadenar la descarga. Además, desde VSS leerlos daría ceros que se guardarían como versión válida sin que nadie lo detectara. Decisión del usuario y del coordinador en HU-08 (motor y revisión de seguridad). |
| ADR-20 | **Resolución controlada de los orígenes** (§8.3 "Resolución controlada de los orígenes"). El servicio nunca deja que el sistema siga un punto de reanálisis al abrir la ruta de un origen (validación, `SaveJobAsync`, inicio de cada ejecución, `%ProgramData%`). La recorre componente a componente: cada uno se abre **relativo al handle del padre** con `NtCreateFile` (`RootDirectory`, un solo componente, `FILE_OPEN_REPARSE_POINT \| FILE_OPEN_FOR_BACKUP_INTENT`); si es un sustituto de nombre, su destino se lee con `FSCTL_GET_REPARSE_POINT` sobre ese mismo handle y solo se continúa si es un volumen local (`\??\X:\…` o `\??\Volume{guid}\…`); cualquier otro destino da `SourceNotLocal` **sin abrirlo**. Tope de 63 saltos; `GetFinalPathNameByHandle` se mantiene como defensa en profundidad. Las rutas de origen se validan y se guardan **normalizadas** (§7.5 "Ruta de origen"). Se activa además **Redirection Guard** (`SetProcessMitigationPolicy(ProcessRedirectionTrustPolicy)` con `EnforceRedirectionTrust`) al arrancar, como defensa complementaria y no como sustituto. Códigos `SourceUnreadable` y `SourcePathInvalid` en el contrato 1.3. | Abrir "siguiendo" los puntos de reanálisis (lo que decía antes §8.3) hace que SYSTEM resuelva dentro de `CreateFile` un enlace plantado por un usuario en cualquier componente: un enlace simbólico hacia `\\atacante\r`, o un *junction* hacia `\RPC Control` más un enlace del administrador de objetos hacia `\??\UNC\…` (sin privilegios), hace que el equipo se autentique con NTLM de su cuenta ante el atacante (*relay* a LDAP o ADCS en un dominio), y comprobar la ruta final después llega tarde (revisión de seguridad de HU-07, ALTA-1). `OBJ_DONT_REPARSE` no sirve como mecanismo principal porque falla sin devolver handle (`STATUS_REPARSE_POINT_ENCOUNTERED`) y no deja leer el destino sobre el mismo objeto; con un solo componente relativo a un handle ya abierto no queda ningún componente intermedio que el sistema pueda volver a resolver, y `FILE_OPEN_REPARSE_POINT` hace que el último se abra sin seguirlo. Abrir prefijos crecientes por ruta completa no vale: cada apertura vuelve a resolver por nombre los componentes ya comprobados (TOCTOU). Redirection Guard solo impide seguir *junctions* creados por usuarios no administradores (no enlaces simbólicos ni enlaces del administrador de objetos), así que no basta solo; como el servicio ya no sigue ningún punto de reanálisis por el sistema, no rompe ADR-13, ADR-14, ADR-18 ni los *junctions* de compatibilidad de un perfil (los crea el sistema). Revisión de seguridad de HU-07, decisión del coordinador. |
| ADR-21 | **`SeBackupPrivilege` solo en los hilos de lectura de orígenes** (§8.2 "Token de lectura de los orígenes"). El servicio activa `SeBackupPrivilege` en una **copia** del token del proceso (`DuplicateTokenEx`, `TokenImpersonation`, `SecurityImpersonation`) de la que **quita** (`SE_PRIVILEGE_REMOVED`) `SeRestorePrivilege`, `SeTakeOwnershipPrivilege`, `SeSecurityPrivilege`, `SeDebugPrivilege` y `SeImpersonatePrivilege`, y la asigna con `SetThreadToken` solo a los hilos dedicados que abren orígenes: `SourceFileSystem` y la resolución controlada de ADR-20 (validación, `SaveJobAsync`, inicio de cada ejecución, cálculo de `PD`), para que validación y ejecución lean lo mismo. Nunca se activa en el token del proceso. Esas aperturas solo piden acceso dentro de `GENERIC_READ \| FILE_LIST_DIRECTORY \| FILE_READ_ATTRIBUTES \| SYNCHRONIZE` con `FILE_OPEN`, comprobado en código. Nada que escriba (la restauración, §8.6; los almacenes, ADR-14) corre en esos hilos. Si no se puede preparar la copia, se lee sin el privilegio con aviso en el log. ADR-16 no cambia. Los archivos cifrados con EFS siguen dando `ReadError`. El instalador fija los privilegios del servicio con `SERVICE_CONFIG_REQUIRED_PRIVILEGES_INFO`: `SeBackupPrivilege`, `SeImpersonatePrivilege` y `SeChangeNotifyPrivilege`, ninguno más (§10; cierre de HU-08 servicio, decisión del coordinador). | §8.2 pedía `FILE_FLAG_BACKUP_SEMANTICS` "para leer como SYSTEM con semántica de copia de seguridad" sin decir cómo; sin el privilegio activado la marca no salta ninguna ACL y SYSTEM no lee los archivos cuya DACL no le da acceso (perfiles con ACL restringidas), que son justo los que el usuario espera tener copiados. El privilegio concede todo acceso de **lectura** saltándose la DACL, así que se limita al mínimo: un token de hilo que no puede escribir saltándose ACL (`SeRestorePrivilege`), tomar la propiedad, tocar la SACL, depurar procesos ni suplantar, y aperturas de solo lectura. La protección de la carpeta de datos sigue siendo por ruta, antes (motor) y después (ruta final) de abrir (ADR-16, ADR-18); lo que el privilegio no cubre es un enlace duro hacia `credentials\*.bin`, que, con el comportamiento actual de Windows, exige poder abrir el destino con escritura de atributos y por tanto un usuario estándar no puede crear (no está documentado como garantía: se comprueba en PM-HU08-01). Revisión de seguridad del `SourceFileSystem` de HU-08, decisión del coordinador. |
