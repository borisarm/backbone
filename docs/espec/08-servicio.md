## 8. Servicio de Windows

### 8.1 Registro

| Propiedad | Valor |
|---|---|
| Nombre | `BackboneService` |
| Nombre para mostrar | Backbone — Copias de seguridad |
| Cuenta | LocalSystem |
| Inicio | Automático (inicio retrasado) |
| Recuperación | Reiniciar a 1 min, 1 min, 5 min; reiniciar contador tras 1 día |
| Dependencias | `LanmanWorkstation` |
| Apagado | Señal de cancelación a la ejecución en curso; se espera hasta 20 s (`HostOptions.ShutdownTimeout`) |

El ejecutable funciona también como aplicación de consola (`--console`) para depurar sin instalar.

### 8.2 Componentes internos

| Componente | Responsabilidad |
|---|---|
| `JobStore` | Lee y escribe `config\jobs.json` con escritura atómica; notifica cambios. |
| `SettingsStore` | `config\settings.json`: usuarios autorizados, pausa, preferencias de notificación, periodo de gracia. |
| `CredentialStore` | Cifra y descifra con DPAPI de ámbito equipo mediante `IDataProtector` (`DpapiMachineProtector`: `CryptProtectData`/`CryptUnprotectData` por `LibraryImport` con `CRYPTPROTECT_LOCAL_MACHINE \| CRYPTPROTECT_UI_FORBIDDEN` y entropía propia; el texto en claro que devuelve el sistema se pone a cero y se libera con `LocalFree`, ADR-07); un archivo por raíz de recurso (`\\servidor\recurso`) en `credentials\` (§8.3). |
| `HistoryStore` | SQLite `data\history.db`: tablas `runs`, `run_issues`; migraciones versionadas; purga de más de 1 año. |
| `Scheduler` | Calcula la próxima ejecución de cada trabajo con `TimeProvider`; cola FIFO de un solo ejecutor; recuperación de ejecuciones perdidas; escucha cambios de configuración, de energía y de red. |
| `JobRunner` | Orquesta una ejecución: condiciones → conexión SMB → bloqueo → VSS → `BackupEngine` → snapshot → retención → historial → eventos. |
| `ShareConnector` | `WNetAddConnection2` sin letra de unidad con las credenciales guardadas; `WNetCancelConnection2` al final; traduce códigos Win32 a `BackboneErrorCode`. Solo lo llama `ShareConnectionManager`. |
| `ShareConnectionManager` | Punto único de conexión al NAS (HU-05, decisión del coordinador; ver "Conexiones al NAS", abajo). |
| `LocalFileSystemInspector` | `ILocalFileSystemInspector`: resolución controlada de los orígenes (ADR-20, §8.3) y búsqueda de las carpetas apartadas. La usan la validación de trabajos, el `JobRunner` al empezar cada ejecución y el cálculo de las carpetas protegidas. Abre en los mismos hilos dedicados y con el mismo token que `SourceFileSystem` (ADR-21). |
| `SourceFileSystem` | Implementa `ISourceFileSystem` de Core (lectura de los orígenes, también desde la instantánea VSS) por handle, relativo a la carpeta padre y sin seguir puntos de reanálisis, en hilos dedicados con el token de ADR-21 (ver abajo). |
| `VssSnapshotter` | Crea y elimina instantáneas VSS (WMI `Win32_ShadowCopy` o API COM de VSS); traduce rutas del origen a la ruta del dispositivo de la instantánea. Garantiza la eliminación con `finally` y limpia al arrancar instantáneas huérfanas creadas por Backbone. |
| `PowerManager` | `SetThreadExecutionState`; estado de batería; eventos de suspensión y reanudación (`SystemEvents` / `RegisterPowerSettingNotification`). |
| `NetworkMonitor` | Cambios de red y coste de la conexión (Network List Manager / `NetworkInformation`). |
| `EventLogWriter` | Escribe en el registro Aplicación con el origen `Backbone`. |
| `IpcServer` | Bucle de aceptación de pipes, `PipeSecurity`, una instancia de `JsonRpc` por cliente, difusión de eventos. |

**Acceso a los archivos de la carpeta de datos (ADR-14).** Todos los almacenes (`JobStore`, `SettingsStore`, `CredentialStore`, `HistoryStore` y cualquier otro que lea o escriba en `%ProgramData%\Backbone`) siguen estas reglas:

- **Carpeta padre**: los almacenes **no crean carpetas**. Las subcarpetas fijas (`config\`, `credentials\`, `data\`, `logs\`) las crea el servicio al arrancar (§8.3); si la carpeta padre de un archivo no existe, la operación falla. Antes de abrir el archivo, la carpeta padre se abre por handle con `CreateFile` y `FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_BACKUP_SEMANTICS`, **sin `FILE_SHARE_DELETE`**, y sobre ese handle se comprueba que es una carpeta, que no es un punto de reanálisis y que su propietario es SYSTEM o Administradores; si no, se rechaza como un archivo. Ese handle se mantiene abierto durante toda la operación (lectura, escritura atómica o apartado a `.bad`), de modo que nadie puede renombrar la carpeta ni sustituirla por un *junction* a mitad.
- **Lectura**: cada archivo se abre por handle con `CreateFile` y `FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_BACKUP_SEMANTICS` (nunca se sigue un punto de reanálisis; la segunda marca permite abrir, y rechazar, una carpeta o un *junction* que ocupe el nombre). Sobre **ese mismo handle**, antes de leer nada, se comprueba con `GetFileInformationByHandleEx` (`FileAttributeTagInfo`) que no es un punto de reanálisis **ni una carpeta**, con `GetFileInformationByHandleEx` (`FileStandardInfo`, `NumberOfLinks`) que tiene **un solo nombre** (no es un enlace duro) y con `GetSecurityInfo` (`OWNER_SECURITY_INFORMATION`) que su propietario es `S-1-5-18` (SYSTEM) o `S-1-5-32-544` (Administradores). Si no se cumple cualquiera de las cuatro, el archivo **se rechaza** (no se lee) y se registra. El contenido se lee de ese handle, no volviendo a abrir la ruta.
- **Escritura atómica**: el temporal se crea con `CreateFile` (`CREATE_NEW`) pasando un **descriptor de seguridad explícito** (propietario Administradores, DACL protegida canónica de RNF-07: solo SYSTEM y Administradores, control total), de modo que nunca existe con otra ACL ni hereda ACE de la carpeta; se escribe y se vuelca a disco (`FlushFileBuffers`) por handle. Antes de reemplazarlo, el destino existente se comprueba con las mismas reglas que en la lectura. El reemplazo es un renombrado **por handle** del temporal (`SetFileInformationByHandle` con `FileRenameInfoEx`, `FILE_RENAME_FLAG_POSIX_SEMANTICS | FILE_RENAME_FLAG_REPLACE_IF_EXISTS`; si el volumen no lo admite, `FileRenameInfo` con `ReplaceIfExists`), que sustituye la entrada del destino sin seguirla. Si algo falla, el temporal se borra por handle (`FileDispositionInfo`).
- **`settings.json` rechazado en el arranque** (punto de reanálisis, es una carpeta, enlace duro, propietario no fiable o carpeta `config\` rechazada): el servicio **no arranca**, registra el evento **1002** (§8.5) y el SCM aplica la recuperación. El tratamiento de un rechazo en otros archivos lo define la historia de cada almacén, sin leer nunca el contenido rechazado.
- **`settings.json` rechazado al escribir después del arranque** (p. ej. alguien lo ha sustituido entre medias): **no se escribe nada**, la configuración en memoria (incluida la lista de usuarios autorizados) no cambia, se registra un error en el log y la operación IPC que pedía el cambio falla. El siguiente arranque lo rechaza (1002).
- **`settings.json` dañado** (JSON no válido o más de 1 MiB, pero con propietario fiable, un solo nombre y sin punto de reanálisis): se registra un aviso y el servicio arranca **fallando cerrado** (configuración por defecto, sin usuarios autorizados). Antes de la siguiente escritura se aparta con las reglas de "Copias apartadas `.bad`" (abajo) a `settings.json.bad-<marca>`; **no se copia** ni se vuelve a leer.
- **Copias apartadas `.bad`** (revisión de seguridad de HU-07, BAJA-3; decisión del coordinador). Son las mismas reglas para `settings.json` y `jobs.json`, y **nunca se sobrescribe** una copia anterior:
  - **Nombre**: `<archivo>.bad-<marca>`, con la marca en UTC del `TimeProvider` con precisión de 100 ns: `yyyyMMddTHHmmssfffffffZ`, p. ej. `jobs.json.bad-20261121T0930123456789Z`. Así el orden por nombre (ordinal) es el orden cronológico.
  - **Apartado**: el archivo dañado se abre y se valida con las reglas de lectura. Después se renombra **por handle**, en la misma carpeta y **sin reemplazar** (`FileRenameInfo` sin `ReplaceIfExists`). Si el nombre ya existe, la operación falla y no se escribe nada.
  - **Como mucho 5 copias por archivo**. Antes de apartar, se enumeran por el handle de `config\` las entradas `<archivo>.bad-*`. Si ya hay 5 o más, se borra la **más antigua** por handle (`FileDispositionInfo`), validada antes con las reglas de lectura. Si no es fiable, no se borra, no se aparta ni se escribe nada, y la operación falla como un archivo rechazado al escribir. Si la enumeración falla, también.
  - Un `<archivo>.bad` sin marca, de una versión anterior, no se toca ni cuenta.
  - Cada apartado se registra en el log con el nombre de la copia. Ni el log ni el evento 1004 llevan el contenido.
- **`jobs.json` rechazado en el arranque** (punto de reanálisis, es una carpeta, enlace duro o propietario no fiable; decisión del coordinador en HU-07): igual que `settings.json`, el servicio **no arranca**, registra el evento **1002** (§8.5) y el SCM aplica la recuperación. Arrancar sin trabajos dejaría de hacer copias sin que nadie lo notara, y apartar el archivo destruiría una configuración que quizá solo tenga mal el propietario.
- **`jobs.json` rechazado al escribir después del arranque**: igual que `settings.json`. No se escribe nada, los trabajos en memoria no cambian, se registra un error en el log y la operación IPC que pedía el cambio falla. El siguiente arranque lo rechaza (1002).
- **`jobs.json` dañado** (JSON no válido o más de **64 MiB**, pero con propietario fiable, un solo nombre y sin punto de reanálisis; decisión del coordinador en HU-07): el servicio **arranca sin trabajos** y registra el evento **1004** (§8.5) en el Visor de eventos, además del log. Sin el evento pasaría desapercibido, porque la app, al no ver trabajos, mostraría el asistente de primer uso como en una instalación nueva. Antes de la siguiente escritura se aparta a `jobs.json.bad-<marca>` con las reglas de "Copias apartadas `.bad`" (renombrado por handle validado sobre ese handle, sin copiar ni volver a leer, sin sobrescribir ninguna copia anterior y con 5 como máximo).

**Conexiones al NAS (HU-05, decisión del coordinador).** Todas las conexiones al NAS pasan por `ShareConnectionManager.AcquireAsync`, nunca por `IShareConnector` directamente: prueba de conexión, validación y guardado de trabajos, copias, restauraciones y mantenimiento.

- **Una conexión por raíz de recurso** (`\\servidor\recurso` normalizada, §7.5 A-3), con recuento de referencias. Cada `AcquireAsync` devuelve un objeto que se libera con `DisposeAsync`. Solo la **última** liberación llama a `WNetCancelConnection2`.
- **Un usuario por servidor**: Windows solo admite un usuario por servidor en la sesión del servicio (error 1219, `ERROR_SESSION_CREDENTIAL_CONFLICT`). HU-05 lo implementa comparando una huella HMAC-SHA-256 de usuario y contraseña (clave aleatoria en memoria) y responde `CredentialsRejected` sin llamar a Windows si no coincide. **Eso es un oráculo de contraseñas** (revisión final de seguridad de HU-05, M-1): con una conexión viva, por ejemplo de una copia, una prueba con credencial explícita contra el mismo servidor termina bien si usuario y contraseña coinciden y da `CredentialsRejected` al instante si no, sin tocar el NAS. Así se puede adivinar la contraseña guardada. **Regla definitiva** (decisión del coordinador; obligatoria antes de que las copias usen el gestor, HU-14):
  - La reutilización se decide por la **identidad** de la credencial guardada (raíz del recurso más su `UpdatedUtc`, que cambia con cada `SaveCredentialAsync`), **nunca por su contenido**. Una petición con credencial guardada comparte la conexión viva de esa raíz solo si esta se hizo con esa misma identidad.
  - Una **credencial explícita no guardada** (la de `TestConnectionAsync` con `credential` distinto de `null`) **nunca comparte** una conexión ajena.
  - Si ya hay otra conexión viva con ese **servidor** (con cualquier recurso) que no se puede compartir según lo anterior, se responde **`NasBusy`** (1018, contrato 1.3) sin llamar a Windows. El código es el mismo coincida o no el secreto. Ya no se calcula huella de la contraseña.
  - **Rechazos seguidos por SID**: tras **5** `CredentialsRejected` seguidos de un mismo SID (cualquier servidor) en `TestConnectionAsync`, sus pruebas con credencial explícita responden `NasBusy` sin conectar durante **5 min**. Una prueba correcta pone el contador a cero. Los contadores están en memoria. Acota el ataque en línea contra el NAS desde la cuenta del equipo (el NAS ve siempre la misma IP).
- **Desconexión pendiente** (B-1): entre la última liberación y la llamada a `WNetCancelConnection2`, que se hace fuera del cerrojo, la raíz queda en estado **cerrando**. Un `AcquireAsync` de esa raíz que llega entonces **espera** a que termine la desconexión y después conecta de nuevo. Si no esperara, conectaría y la desconexión pendiente lo dejaría sin conexión.
- **Pruebas de conexión** (`TestConnectionAsync`): como mucho una a la vez por servidor y dos en total en todo el servicio. El límite de dos cuenta también las operaciones **abandonadas** por el plazo (11 s) que aún no han vuelto. Los semáforos por servidor se liberan (y se descartan) cuando quedan libres, para no acumular uno por cada nombre probado (B-2).
- **Parada del servicio** (B-2): el gestor queda **cerrado** y todo `AcquireAsync` posterior lanza una excepción. Se esperan como mucho 5 s a que terminen las liberaciones en curso. Después se llama a `WNetCancelConnection2` con `fForce = TRUE` para las conexiones que queden, y las que aún estén en curso se desconectan a la fuerza cuando terminen. El código 2250 (`ERROR_NOT_CONNECTED`, la conexión ya no existía) no se registra como desconexión forzada.
- **Archivo de prueba** (B-3): en "Probar conexión", la ruta final del archivo de prueba se comprueba **sobre su handle ya abierto y antes de escribir** (`GetFinalPathNameByHandle`), y tiene que estar dentro de la raíz conectada. Si no se puede obtener, cuenta como fallo (`AccessDenied`).
- **Sesión de inicio compartida** (informativo): todos los servicios que corren como LocalSystem comparten la sesión de inicio `0x3e7`, y las conexiones de `WNetAddConnection2` son por sesión de inicio. Por tanto, desconectar una raíz también la quita a otros procesos de SYSTEM que la usaran, y una conexión de otro servicio de SYSTEM con ese servidor provoca 1219 al conectar. Backbone solo desconecta las raíces que ha conectado él (recuento propio), pero no puede saber si otro proceso de SYSTEM las usa a la vez.
**Lectura de los orígenes (`ISourceFileSystem`, revisión de seguridad de HU-13, MEDIA-2).** El motor solo accede a los orígenes mediante `ISourceFileSystem` (Core); la implementación del servicio (`SourceFileSystem`, HU-08/HU-15) cumple este contrato en sus tres operaciones:

- **`EnumerateAsync`, `OpenReadAsync` y `GetFileInfoAsync` abren por handle, relativo a la carpeta padre y sin seguir puntos de reanálisis** ("Apertura relativa", abajo; ADR-18): `NtCreateFile` con `RootDirectory` = handle de la carpeta padre, `ObjectName` = un solo componente y `FILE_OPEN_REPARSE_POINT | FILE_OPEN_FOR_BACKUP_INTENT` (los equivalentes de `FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_BACKUP_SEMANTICS`), en carpetas y en archivos, con el token de lectura de ADR-21 ("Token de lectura de los orígenes", abajo). Ya no se usa `CreateFile` con la ruta completa.
- Sobre **ese mismo handle**, antes de leer nada, comprueban con `GetFileInformationByHandleEx` (`FileAttributeTagInfo`) los atributos y la **etiqueta** de reanálisis, y que es carpeta o archivo según lo pedido. Lo que hacen depende de la clase de la etiqueta ("Clasificación por etiqueta", abajo; ADR-19). Si es un **enlace**, lanzan `SourceAccessException` con `RunIssueCode.ReparsePointSkipped` y no lo siguen: el motor lo omite con ese aviso (RF-06).
- **La enumeración se hace desde ese handle** (`GetFileInformationByHandleEx` con `FileIdBothDirectoryInfo`), no volviendo a abrir la ruta. El contenido se lee del handle de `OpenReadAsync` ("Apertura para leer el contenido", abajo) y los metadatos de `GetFileInfoAsync`, del suyo. Cada elemento enumerado lleva en `SourceEntry.Attributes` los atributos tal como los da el sistema y en `SourceEntry.ReparseTag` su etiqueta. En `FILE_ID_BOTH_DIR_INFO` la etiqueta va en `EaSize` cuando el elemento tiene `FILE_ATTRIBUTE_REPARSE_POINT`; si no lo tiene, vale 0. `GetFileInfoAsync` la toma de `FileAttributeTagInfo`. El motor clasifica cada elemento con esos dos valores antes de abrirlo.
- **Dos enumeraciones simultáneas de la misma raíz** (cierre de HU-08 servicio): la enumeración avanza un cursor sobre el handle fijo de la raíz del origen, que no se puede compartir entre dos recorridos. Si se pide una mientras otra de la misma raíz está en curso, la nueva lanza `SourceAccessException(ReadError)` sin tocar el handle. El motor no lo hace nunca (recorre en profundidad y de una en una).
- **Cambio en `SourceEntry` (HU-08)**: el tipo gana la propiedad `uint ReparseTag { get; init; }`, con valor por defecto 0 (sin punto de reanálisis), declarada en el cuerpo del `record` y no como parámetro posicional, para que los simuladores y las pruebas existentes sigan compilando. Si `Attributes` no tiene `FileAttributes.ReparsePoint`, la etiqueta es 0 y el motor la ignora. Si lo tiene y la etiqueta es 0 (implementación que no la rellena), el motor lo trata como **no legible**, nunca como *normal*. **La firma de `ISourceFileSystem` no cambia** (ADR-18). `SourceEntry` es un tipo de `Backbone.Core`, no de `Backbone.Contracts`: el contrato IPC no cambia de versión.
- **Ruta final sobre el mismo handle (revisión de seguridad final de HU-13, M-A)**. `FILE_FLAG_OPEN_REPARSE_POINT` solo afecta al **último** componente de la ruta: en una copia en vivo (sin VSS, RF-22) un usuario puede sustituir una carpeta **intermedia** ya enumerada (p. ej. `C:\Users\alice\A`) por un *junction* hacia `C:\ProgramData\Backbone`, y al abrir después `…\A\credentials\x.bin` la ruta se resolvería a través del enlace. Por eso, en las tres operaciones, tras abrir el elemento y antes de leer nada, la implementación obtiene sobre **ese mismo handle** su ruta final (`GetFinalPathNameByHandle` con `FILE_NAME_NORMALIZED | VOLUME_NAME_NT`, que vale igual dentro de una instantánea VSS, que no tiene letra de unidad) y comprueba:
  1. que es **exactamente la esperada**: la ruta final de la raíz del origen más la ruta relativa del elemento, por segmentos completos: los de la raíz, en comparación ordinal sin distinguir mayúsculas; los de la ruta relativa, con `Ordinal` (carpetas que distinguen mayúsculas, "Apertura relativa", abajo; cierre de HU-08 servicio). La ruta final de la raíz se obtiene una vez al empezar la ejecución sobre el handle de la raíz (`ReadPath`), abierta como dice "Apertura relativa" (abajo); la ruta relativa es lo que sigue a la raíz en la ruta recibida;
  2. que la ruta relativa **no cae dentro de una carpeta protegida**: no es ni empieza por ninguna de las exclusiones obligatorias del origen (§8.3, capa 2). Es defensa en profundidad, porque el motor no las pide nunca.

  Si no se cumple cualquiera de las dos, lanza `SourceAccessException` con `RunIssueCode.ReparsePointSkipped` (el motor omite el elemento como en RF-06) y no lee nada del handle. Como la comprobación se hace sobre el handle ya abierto, lo que se lee es justo el objeto comprobado, aunque el enlace se deshaga después. Con la apertura relativa (abajo) esta comprobación es **defensa en profundidad**: se mantiene, pero ya no es lo que impide seguir un enlace intermedio.
- **Apertura relativa (obligatoria; revisión de seguridad del `SourceFileSystem` de HU-08, A-1; ADR-18).** La comprobación de la ruta final llega **después** de abrir: con `CreateFile` y la ruta completa (`\\?\C:\…\A\B`), si `A` pasa a ser un *junction* hacia `\RPC Control` con un enlace del administrador de objetos hacia `\??\UNC\atacante\x` en el momento justo (por ejemplo, con un oplock sobre un archivo de la carpeta para detener la copia), el sistema resuelve el enlace dentro de la apertura y SYSTEM se autentica con NTLM ante el atacante en una copia en vivo, el mismo vector que ADR-20. Por eso, **en vivo y en VSS** (por uniformidad, aunque la instantánea sea de solo lectura):
  - **Cada elemento** se abre con `NtCreateFile`: `OBJECT_ATTRIBUTES.RootDirectory` = handle de su carpeta padre, `ObjectName` = **un solo** componente (el nombre enumerado, sin `\`), **sin `OBJ_CASE_INSENSITIVE`** (cierre de HU-08 servicio: el nombre sale de la enumeración con su grafía exacta y, en una carpeta que distingue mayúsculas, la apertura sin distinguir podría llegar a otra entrada; solo las aperturas de la raíz del volumen y de los componentes de la ruta de la raíz del origen llevan `OBJ_CASE_INSENSITIVE`, como hasta ahora), disposición `FILE_OPEN` y opciones `FILE_OPEN_REPARSE_POINT | FILE_OPEN_FOR_BACKUP_INTENT | FILE_COMPLETE_IF_OPLOCKED` ("Plazo", abajo). Las carpetas, además, con `FILE_DIRECTORY_FILE | FILE_SYNCHRONOUS_IO_NONALERT` (la enumeración es síncrona y se cancela con `CancelSynchronousIo`); los archivos, con `FILE_NON_DIRECTORY_FILE` y sin `FILE_SYNCHRONOUS_IO_*` (E/S asíncrona, que se cancela con `CancelIoEx`). No se usa `OBJ_DONT_REPARSE`, por lo dicho en §8.3 (paso 2 de la resolución controlada).
  - **SQOS de identificación**: `OBJECT_ATTRIBUTES.SecurityQualityOfService` apunta a un `SECURITY_QUALITY_OF_SERVICE` con `ImpersonationLevel = SecurityIdentification`, `ContextTrackingMode = SECURITY_STATIC_TRACKING` y `EffectiveOnly = TRUE`. Si, pese a todo, una apertura llegara a un servidor remoto o a un pipe, este no podría suplantar a SYSTEM. **No** se usa `SECURITY_SQOS_PRESENT` en `CreateFile`/`ReOpenFile`: tiene el mismo valor que `FILE_FLAG_OPEN_NO_RECALL` y cambiaría el significado de la llamada.
  - **La raíz de cada origen** sale de la resolución controlada de ADR-20 (§8.3), y su handle es el primer padre. **En vivo** (cierre de HU-08 servicio, decisión del coordinador), `SourceFileSystem` **no recibe** el handle de la resolución: vuelve a bajar hasta `ReadPath` desde la raíz del volumen, abierta por `\??\Volume{guid}\` o, si `ReadPath` lleva letra, por `\??\X:\` tras **repetir** `GetDriveType` justo antes de abrirla, con la misma regla que el paso 1 de la resolución controlada (BAJA-5, BAJA-N1): todo lo que no sea `DRIVE_FIXED` se rechaza **sin abrir nada** y el origen da `SourceRootUnreadable`; con `DRIVE_NO_ROOT_DIR` la causa es "no encontrado". Así una letra reasignada a una unidad de red después de la resolución no se abre ni provoca autenticación (PM-HU08-02). Después se comprueba, sobre el handle, `FileFsDeviceInformation` como en el paso 1 de la resolución controlada. A continuación baja componente a componente con las reglas de esta sección **sin seguir ningún enlace**: como `ReadPath` es la ruta final de la resolución, no debe contener ninguno, y un componente que sea un enlace (o que no sea una carpeta *normal* o de la lista blanca) aparecido después de la resolución da `SourceRootUnreadable` (§8.4). Por eso `ReadPath` tiene que ser la ruta final de la resolución, nunca la configurada (requisito de HU-14, §8.3 punto 6). En VSS, la raíz se abre igual pero sobre el dispositivo de la instantánea ("Rutas y raíces", abajo): `\Device\HarddiskVolumeShadowCopy<n>\` por `NtCreateFile` y después componente a componente hasta `ReadPath`; cualquier componente que no sea una carpeta sin punto de reanálisis o de la lista blanca da `SourceRootUnreadable`.
  - **Caché de carpetas**: la implementación mantiene abiertos los handles de las carpetas en recorrido, por ruta relativa al origen. El handle de la raíz de cada origen está fijo durante toda la ejecución; aparte, como mucho **128** handles de carpeta por ejecución, con expulsión del usado hace más tiempo (LRU) y nunca de uno que esté en uso en una operación. 128 supera con holgura la profundidad habitual, así que en un recorrido en profundidad (el del motor) casi siempre está abierto el padre. **Si el padre no está en la caché** (expulsado, o una ruta que el motor pide fuera de orden), se abre desde el antepasado abierto más cercano (como último recurso, la raíz) **componente a componente**, con las mismas reglas: cada carpeta intermedia se clasifica sobre su handle y, si ya no es una carpeta *normal* o de la lista blanca, la operación pedida lanza `SourceAccessException` con el código de su clase (`ReparsePointSkipped`, `CloudOnlySkipped` o `ReadError`) sin abrir nada debajo. Cada apertura de ese camino cuenta para el plazo y el presupuesto. Superar el límite solo cuesta aperturas de más, nunca se abre por ruta completa ni se rechaza nada legítimo.
  - Las carpetas de la caché se abren con acceso `FILE_LIST_DIRECTORY | FILE_READ_ATTRIBUTES | SYNCHRONIZE` y compartición de lectura, escritura **y borrado**: no se impide al usuario renombrar ni borrar sus carpetas durante una copia que puede durar horas. Es seguro porque el handle sigue apuntando al mismo objeto: si la carpeta se mueve, lo que se abre debajo sigue siendo su contenido, y la ruta final (defensa en profundidad) ya no coincide y da `ReparsePointSkipped`. Los handles de archivo siguen sin `FILE_SHARE_DELETE` mientras se leen ("Apertura para leer el contenido", abajo).
  - **`STATUS_OPLOCK_BREAK_IN_PROGRESS` es un éxito** (`NT_SUCCESS`): la comprobación del resultado de `NtCreateFile` no puede ser `== STATUS_SUCCESS`.
  - **Archivo sustituido por una carpeta o un *junction*** (cierre de HU-08 servicio): si la apertura de un archivo falla porque el nombre ya no es un archivo (`FILE_NON_DIRECTORY_FILE` da `STATUS_FILE_IS_A_DIRECTORY`), el elemento se reabre, relativo al mismo padre y con las mismas opciones salvo `FILE_NON_DIRECTORY_FILE`, **solo con `FILE_READ_ATTRIBUTES`** (más `SYNCHRONIZE`), para clasificarlo sobre ese handle sin poder leer nada. Si es un *junction* (o cualquier enlace), `SourceAccessException(ReparsePointSkipped)`. Si es una **carpeta real** (no un enlace), `SourceAccessException(ReadError)`: el motor conserva la versión anterior del archivo (RF-25) y no entra en la carpeta en esa ejecución; la siguiente la enumerará como carpeta.
  - **Nombres bajo la raíz, con distinción de mayúsculas** (cierre de HU-08 servicio): NTFS admite carpetas que distinguen mayúsculas (`FILE_CASE_SENSITIVE_DIR`), donde `a` y `A` son elementos distintos. Por eso los segmentos que siguen a `ReadPath` (la ruta relativa, en la caché de carpetas, al quitar el prefijo y en la comprobación de la ruta final, arriba) se comparan con `StringComparison.Ordinal`. La raíz `ReadPath` y su ruta final se siguen comparando sin distinguir mayúsculas.
- **Rutas y raíces**: `ISourceFileSystem` **no cambia de firma** (decisión de la revisión final de HU-13): las rutas siguen siendo opacas para el motor. La implementación se crea **por ejecución** con la lista de orígenes (`BackupSource`: `ReadPath` y exclusiones obligatorias) y deduce la ruta relativa de cada ruta recibida quitando el prefijo `ReadPath\` de su origen; rechaza (`SourceAccessException` con `PathInvalid`) una ruta que no empiece por la raíz de un origen de la ejecución o que tenga segmentos vacíos, `.` o `..`. Como las rutas las compone la propia implementación (raíz + `\` + nombre enumerado), esto no rechaza nada legítimo.
  - **Raíces de dispositivo** (B-2): una `ReadPath` con la forma `\\?\GLOBALROOT\Device\<dispositivo>\…` solo se admite si `<dispositivo>` es `HarddiskVolumeShadowCopy<n>` (la instantánea VSS; `<n>` solo dígitos ASCII decimales, sin signo ni ceros a la izquierda) o, si hiciera falta para un volumen sin letra, `HarddiskVolume<n>` con la misma regla. Cualquier otro dispositivo (`Mup`, `LanmanRedirector`, `NamedPipe`, `Harddisk0\…`, nombres con más segmentos…) se rechaza al crear la implementación (`ArgumentException`: es un error de programación del servicio, no del usuario) y la ejecución termina `Failed` con `Internal`. Además, en VSS el dispositivo tiene que ser uno de los que `VssSnapshotter` ha creado para **esta** ejecución, y sobre el handle de su raíz se comprueba `FileFsDeviceInformation` como en el paso 1 de la resolución controlada (disco, no remoto, no extraíble).
  - **Exclusiones obligatorias** (I-4): cada una se divide en segmentos por `\` **y por `/`** (cierre de HU-08 servicio: así una exclusión escrita con `/` no deja de aplicarse). Si tras dividirla queda vacía o tiene algún segmento vacío, `.` o `..`, es un error de programación del servicio: `ArgumentException` al crear la implementación (la ejecución termina `Failed` con `Internal`), **nunca** se descarta en silencio, porque una exclusión obligatoria perdida dejaría leer la carpeta de datos. Cómo se calculan: §8.3, punto 2.
- **Raíz del origen en VSS**: la ruta de la instantánea (`ReadPath`) se calcula a partir de la **ruta final** del origen obtenida con la resolución controlada de §8.3 (punto 1, ADR-20), no de la ruta configurada; si no, un origen que fuera un *junction* se resolvería dentro de la instantánea hacia el volumen en vivo.
- Así, una carpeta o un archivo sustituido por un *junction* o un enlace simbólico entre la enumeración y la apertura, sea el último componente o uno intermedio, no lleva la lectura de SYSTEM fuera del origen (p. ej. a `%ProgramData%\Backbone`, §8.3).
- Las rutas que recibe son las que devolvió la propia implementación (`SourceEntry.FullPath`) o la raíz `ReadPath` de un origen, ya traducidas a la instantánea VSS cuando la hay; admiten rutas largas (RNF-09).

**Clasificación por etiqueta (ADR-19, decisión del usuario y del coordinador en HU-08).** Cada elemento se clasifica por sus atributos y su etiqueta de reanálisis (`FileAttributeTagInfo` sobre el handle; `SourceEntry.Attributes` y `SourceEntry.ReparseTag` en el motor). El motor lo hace con lo que da la enumeración, antes de abrir nada. `SourceFileSystem` lo repite sobre el handle de cada apertura, antes de leer nada, porque el elemento puede haber cambiado desde que se enumeró:

| Clase | Cuándo | Tratamiento |
|---|---|---|
| **Normal** | Sin `FILE_ATTRIBUTE_REPARSE_POINT` (etiqueta 0) y sin atributos de nube válidos (abajo). | Se lee. |
| **Enlace** | Etiqueta **sustituto de nombre** (bit N, `0x20000000`; `IsReparseTagNameSurrogate`): `IO_REPARSE_TAG_MOUNT_POINT` (*junction* y punto de montaje), `IO_REPARSE_TAG_SYMLINK` y cualquier otra con ese bit. | No se sigue ni se abre. Se omite con `ReparsePointSkipped` y **no** se conserva nada del padre (RF-06). En una carpeta, tampoco lo que tuviera debajo. |
| **Solo en la nube** | Ver "Archivos y carpetas solo en la nube" (abajo). | No se abre (no se descarga). Se omite con `CloudOnlySkipped` y aviso, y conserva la versión del padre. En una carpeta, todo lo que tenía debajo en el padre. |
| **Contenido (lista blanca)** | `IO_REPARSE_TAG_CLOUD*` (etiqueta `& 0xFFFF0FFF == 0x9000001A`, `IO_REPARSE_TAG_CLOUD_MASK`) totalmente descargado; `IO_REPARSE_TAG_WOF` (`0x80000017`; en Windows 11 26320 el filtro oculta esta etiqueta y un archivo WOF se ve como *normal*, "Apertura para leer el contenido"); `IO_REPARSE_TAG_DEDUP` (`0x80000013`). | Se lee **por su contenido** ("Apertura para leer el contenido", abajo). Una carpeta de nube totalmente poblada se recorre. |
| **No legible** | Cualquier otra etiqueta sin bit N: ProjFS (`IO_REPARSE_TAG_PROJFS`), proveedores de sincronización o HSM de terceros, etiquetas desconocidas o futuras, `IO_REPARSE_TAG_APPEXECLINK`… | No se abre ni se recorre. Se omite como ilegible (RF-25): aviso `ReadError` que nombra la etiqueta en hexadecimal, y se conserva la versión del padre (en una carpeta, todo lo que tenía debajo). |

- **Orden**: primero *enlace*, después *solo en la nube*, después *no legible*, y después *contenido* o *normal*. Un sustituto de nombre es siempre un enlace, tenga los atributos que tenga.
- **Motivo de la lista blanca**: cualquier usuario puede registrar su propia raíz de sincronización (`CfRegisterSyncRoot`) o de ProjFS dentro de un origen. Su proveedor atiende entonces las aperturas y lecturas que hace SYSTEM, y puede colgarlas o servir contenido arbitrario. Por eso solo se leen las etiquetas cuyo filtro es del sistema y sirve el contenido local. Los marcadores de la Cloud Files API (`IO_REPARSE_TAG_CLOUD*`) los puede crear cualquier proveedor, no solo OneDrive. Se leen solo cuando están totalmente descargados, y entonces su contenido está en el disco y no hace falta el proveedor ("Apertura para leer el contenido").
- La raíz de un origen sigue la misma clasificación. Una raíz de nube poblada (p. ej. la carpeta de OneDrive) se recorre. Si es un enlace, está solo en la nube o no es legible, el aviso es `SourceRootUnreadable` (§8.4) y se conserva todo el origen del padre.

**Archivos y carpetas solo en la nube (R4, RF-06).**

- **Marcadores visibles**: al arrancar, antes de leer ningún origen, el servicio llama a `RtlSetProcessPlaceholderCompatibilityMode(PHCM_EXPOSE_PLACEHOLDERS)` (`ntdll`, Windows 10 1803 o posterior, por `LibraryImport`). Si devuelve un valor negativo, lo registra como error y las copias que lean orígenes fallan (`Internal`) en lugar de leer con los marcadores disfrazados. La Cloud Files API oculta sus puntos de reanálisis, el bit *sparse* y el *offline* a los procesos que no son motores de sincronización ni tienen su imagen bajo `%SystemRoot%`, y el ejecutable del servicio está en `Program Files`. Sin esta llamada, un marcador no descargado parecería un archivo normal.
- **Archivo solo en la nube**: un archivo con `FILE_ATTRIBUTE_RECALL_ON_OPEN` (`0x00040000`, solo aparece en la enumeración) o `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS` (`0x00400000`). También uno con `FILE_ATTRIBUTE_OFFLINE` (`0x1000`) cuando, además, su etiqueta es de nube (`IO_REPARSE_TAG_CLOUD*`) o de HSM (`IO_REPARSE_TAG_HSM`, `IO_REPARSE_TAG_HSM2`). Los `RECALL_*` solo los pone el modo núcleo. `OFFLINE` lo puede poner cualquier usuario con `SetFileAttributes`: solo, sin etiqueta, no significa nada y el archivo se lee como normal. Con una etiqueta que no sea de nube ni HSM, manda la etiqueta (*enlace* o *no legible*).
- **Sobre el handle** (`OpenReadAsync`, `GetFileInfoAsync`), además de esos atributos, con etiqueta de nube se comprueba `CfGetPlaceholderStateFromAttributeTag(attributes, tag)` (`cldapi`). Con `CF_PLACEHOLDER_STATE_PARTIAL` o `CF_PLACEHOLDER_STATE_PARTIALLY_ON_DISK`, o si devuelve `CF_PLACEHOLDER_STATE_INVALID`, el archivo cuenta como solo en la nube. La función solo interpreta los dos valores y no llama al proveedor.
- Un archivo así **no se abre para leer**, ni en vivo ni en la instantánea VSS. El motor no lo pide (lo ve en la enumeración). Si la implementación lo detecta sobre el handle (el archivo **ha pasado a estar solo en la nube** después de enumerarlo), lanza `SourceAccessException(CloudOnlySkipped)` sin leer nada. En los dos casos se omite con aviso y conserva la versión del snapshot padre si existía, como un ilegible (RF-25): el archivo sigue siendo del usuario, solo que no está en el disco, y una copia no debe perderlo porque se haya liberado espacio. La primera apertura, con `FILE_FLAG_OPEN_REPARSE_POINT`, no pide el procesamiento del filtro de nube y no desencadena la descarga. De ella nunca se lee un marcador no descargado.
- **Defensa en profundidad (sobre todo en VSS)**: con etiqueta de nube, antes de leer se consulta `FSCTL_QUERY_ALLOCATED_RANGES` sobre el handle para todo el tamaño del archivo. Si hay algún rango sin asignar, se lanza `SourceAccessException(CloudOnlySkipped)` en vez de leer. Escenario: un marcador que se ha actualizado en la nube sin descargarse puede quedar en la instantánea con sus atributos de descargado y con huecos. Al leerlo sin el filtro, los huecos saldrían como ceros y se guardarían como una versión válida que nadie detectaría.
- **Carpetas de nube no pobladas** (decisión del coordinador en HU-08, a raíz de QA): una carpeta con `RECALL_ON_OPEN` o `RECALL_ON_DATA_ACCESS`, o con etiqueta de nube y estado `PARTIAL`, **no se recorre**, ni en vivo ni en VSS. Se omite con `CloudOnlySkipped` y conserva del padre todo lo que tenía debajo, como una carpeta ilegible (RF-25, §8.4). Motivo:
  - En vivo, enumerar una carpeta no poblada hace que el filtro pida al proveedor su contenido (`CF_CALLBACK_TYPE_FETCH_PLACEHOLDERS`, "para satisfacer una consulta del directorio"). `PHCM_EXPOSE_PLACEHOLDERS` solo cambia lo que se **ve** de los marcadores, no evita esa llamada. Bajaría metadatos de la red y podría colgarse en un proveedor ajeno.
  - En VSS no hay proveedor. El listado solo tendría lo que está en local, y los hijos que faltan desaparecerían del snapshot como si se hubieran borrado.
  - `OFFLINE` en una carpeta sigue la misma regla que en un archivo.
  - Una carpeta de nube **totalmente poblada** (sin `RECALL_*` ni `PARTIAL`, el caso normal de OneDrive) se recorre, y cada archivo se clasifica por separado. En una máquina con OneDrive, las carpetas de la raíz de sincronización tienen atributos `0x410` y etiqueta `0x9000601A`, sin `RECALL_*`.

**Apertura para leer el contenido.** `FILE_FLAG_OPEN_REPARSE_POINT` desactiva el procesamiento normal del punto de reanálisis. Según la documentación de `CreateFile`, el handle se obtiene "esté operativo o no el filtro que controla el punto de reanálisis", así que **no se garantiza** que lo que se lee sea el contenido real.

- Comprobación hecha en Windows 11 (26320) con `PHCM_EXPOSE_PLACEHOLDERS`: un archivo de OneDrive descargado (etiqueta `0x9000601A`) y uno comprimido con WOF dan el mismo SHA-256 con y sin la marca. WOF, además, no expone su etiqueta: `FileAttributeTagInfo` devuelve etiqueta 0.
- **Consecuencia para WOF** (backbone-service, cierre de HU-08 servicio): en Windows 11 26320 el filtro WOF oculta la etiqueta **incluso** a `FileAttributeTagInfo` sobre un handle abierto con `FILE_OPEN_REPARSE_POINT`, y en la enumeración el elemento tampoco tiene `FILE_ATTRIBUTE_REPARSE_POINT`. Un archivo comprimido con `compact` se clasifica como *normal*: se lee del primer handle y **nunca pasa por la lista blanca de WOF**, ni por la reapertura del punto 2 ni por el tratamiento del punto 3. Lo que lee es lo que sirve el filtro (el contenido descomprimido). La entrada de WOF de la lista blanca se mantiene para el caso de que una versión de Windows sí exponga la etiqueta. Si en VSS el filtro no atendiera la instantánea, lo leído no sería el contenido real y nada lo detectaría por la etiqueta: lo comprueba PM-HU08-01 (paso 7) comparando el SHA-256.
- Con Data Deduplication, el flujo principal de un archivo optimizado es un *stub* y el contenido está en el almacén de fragmentos, que solo sirve `Dedup.sys`.

Por eso:

1. **Primera apertura**, siempre relativa al padre ("Apertura relativa", arriba) con `FILE_OPEN_REPARSE_POINT | FILE_OPEN_FOR_BACKUP_INTENT | FILE_COMPLETE_IF_OPLOCKED`, SQOS de identificación y acceso de lectura (`GENERIC_READ`), sin `FILE_SHARE_DELETE`. Sobre ese handle: clasificación por etiqueta y atributos, y ruta final (ADR-18). Si el elemento es *normal* (sin punto de reanálisis), el contenido se lee de este mismo handle: la opción se ignora cuando no hay punto de reanálisis.
2. Si es de la **lista blanca**, se abre un **segundo handle sin `FILE_OPEN_REPARSE_POINT`** para leer el contenido, reabriendo el primero **relativo a sí mismo**: `NtCreateFile` con `RootDirectory` = primer handle y `ObjectName` vacío (lo mismo que hace `ReOpenFile`, que no vuelve a resolver la ruta), con `FILE_OPEN_FOR_BACKUP_INTENT | FILE_COMPLETE_IF_OPLOCKED | FILE_NON_DIRECTORY_FILE`, SQOS de identificación, acceso `GENERIC_READ` y el token de ADR-21. Se usa `NtCreateFile` y no `ReOpenFile` porque `ReOpenFile` no admite `FILE_COMPLETE_IF_OPLOCKED` ni el SQOS de `OBJECT_ATTRIBUTES`. Si la reapertura relativa a sí mismo no funcionara como se espera (lo comprueban las pruebas de integración de backbone-service), se para y se pregunta; no se vuelve a `CreateFile` por ruta. Mientras tanto el primero se mantiene abierto sin `FILE_SHARE_DELETE`, para que nadie pueda renombrar ni sustituir el elemento.
   - **Justo antes de reabrir** (B-1), se vuelve a leer `FileAttributeTagInfo` del **primer** handle y se comprueba que sigue en la misma clase de la lista blanca. Si no, `SourceAccessException(ReparsePointSkipped)` (o `CloudOnlySkipped`/`ReadError` según su clase nueva) sin reabrir.
   - **Riesgo residual** (R15, §13): entre esa comprobación y la reapertura, quien pueda escribir los atributos del archivo puede cambiar su punto de reanálisis con `FSCTL_SET_REPARSE_POINT`. Para que la reapertura, que ya no lleva `FILE_OPEN_REPARSE_POINT`, siguiera un enlace, la etiqueta nueva tendría que ser un enlace simbólico, y eso exige poder crear enlaces simbólicos (`SeCreateSymbolicLinkPrivilege`). Las comprobaciones del segundo handle (abajo) detectan el cambio, pero después de la apertura.

   Sobre el segundo handle, antes de leer, se comprueba:
   - el mismo identificador de archivo que el primero (`FileIdInfo`: número de serie del volumen e identificador de 128 bits);
   - la misma clase de etiqueta, comprobada otra vez con `FileAttributeTagInfo`;
   - los atributos de nube y el estado del marcador;
   - la ruta final esperada.

   Si algo no coincide, se lanza `SourceAccessException(ReparsePointSkipped)`, o `CloudOnlySkipped` si ha pasado a estar solo en la nube, y no se lee nada.
3. Si el segundo handle **no se puede abrir** porque el filtro propietario no está en la pila (`ERROR_CANT_ACCESS_FILE`, `STATUS_IO_REPARSE_TAG_NOT_HANDLED`), cosa posible en la instantánea VSS:
   - Con **etiqueta de nube**, el contenido de un marcador descargado está entero en el flujo principal. Se lee del **primer** handle solo si `FSCTL_QUERY_ALLOCATED_RANGES` cubre todo el tamaño (ver arriba); si no, `CloudOnlySkipped`.
   - Con **WOF** (solo si la etiqueta es visible, que no es el caso en Windows 11 26320) **o Dedup** no se lee el flujo crudo, que no es el contenido. Se lanza `SourceAccessException(ReadError)` y el archivo se conserva del padre (RF-25).
4. Las carpetas de la lista blanca (carpetas de nube pobladas) se enumeran desde el primer handle. La enumeración no necesita el filtro, porque las entradas están en el disco.

El comportamiento real en VSS de WOF, Dedup y los marcadores de nube se comprueba en PM-HU08-01.

**Plazo de las lecturas de los orígenes.** Toda operación de `SourceFileSystem` que pueda llegar a un filtro tiene un plazo de **60 s**: cada apertura, cada llamada de enumeración y cada lectura de un bloque. Un disco local lento o un antivirus no se acercan a ese valor, y un proveedor colgado no bloquea la copia durante horas.

- **Mecanismo**:
  - Las lecturas usan handles de E/S asíncrona (abiertos sin `FILE_SYNCHRONOUS_IO_*`) y se cancelan con `CancelIoEx`.
  - Las aperturas y enumeraciones, que son síncronas, se hacen en un hilo dedicado ("Token de lectura de los orígenes", abajo) y se cancelan con `CancelSynchronousIo`.
  - El plazo se enlaza con el `CancellationToken` de la ejecución.
  - **Búfer de lectura** (B-3): mide `min(tamaño de bloque, tamaño del archivo)` (al menos 1 byte) o sale de un *pool* al que **solo vuelve** si la lectura terminó sin fallo ni abandono; una lectura abandonada puede seguir escribiendo en él cuando el controlador responda.
- **Oplocks** (revisión del `SourceFileSystem` de HU-08, M-1): un usuario con escritura en un origen puede poner oplocks *batch* o RH sobre sus archivos y carpetas; sin más, cada apertura de SYSTEM esperaría la confirmación de la ruptura, sin límite, hasta el plazo. Por eso **todas** las aperturas de lectura de orígenes (las de `SourceFileSystem`, incluidas la reapertura de la lista blanca y las carpetas de la caché, y las de la resolución controlada de ADR-20) llevan `FILE_COMPLETE_IF_OPLOCKED`: la apertura termina enseguida con `STATUS_OPLOCK_BREAK_IN_PROGRESS` (un éxito) en lugar de bloquear el hilo. No se espera la ruptura (ni `FSCTL_REQUEST_OPLOCK` ni ninguna espera a su notificación). Las operaciones posteriores sobre ese handle que tengan que esperar a la confirmación (p. ej. la lectura de un archivo con oplock *batch*) siguen sujetas al plazo y al presupuesto de abajo.
- **Si vence el plazo**, el elemento se omite con `SourceAccessException(ReadError)` indicando que se superó el plazo, y conserva la versión del padre (RF-25).
- **Presupuesto de plazos por origen y ejecución** (M-1, decisión del coordinador). Cuentan las operaciones **lentas** de ese origen: las que vencen el plazo y, para que un proveedor no se quede justo por debajo de 60 s en cada operación, las que terminan después de **10 s**. El presupuesto se agota con **5 plazos vencidos** o con **10 min acumulados** en operaciones lentas (la duración completa de cada una). Al agotarse:
  - `SourceFileSystem` registra **un** aviso en el log (origen, plazos vencidos y tiempo acumulado) y marca el origen como agotado. Desde entonces, toda operación sobre una ruta de ese origen lanza enseguida, **sin E/S**, `SourceAccessException(ReadError)` con un mensaje que lo dice ("no se ha leído: el origen ha agotado su presupuesto de plazos"). La operación en curso sigue con su propio plazo.
  - El motor lo trata como cualquier ilegible (RF-25): un archivo conserva la versión del padre y una carpeta que no se puede enumerar, todo lo que tenía debajo. Si aún no se había enumerado la raíz, el aviso es `SourceRootUnreadable` (§8.4). Los demás orígenes se siguen leyendo con su propio presupuesto.
  - **No hay código de aviso nuevo** (decisión del arquitecto): se usa `ReadError`, que ya conserva la versión del padre, y el contrato IPC no cambia. Los archivos que quedaban en listados ya abiertos dan un aviso cada uno; los avisos ya están acotados (10 000 y `WarningsTruncated`, §8.4). Un código propio que resumiera el origen en un solo aviso exigiría cambios en el motor y en la app; se puede valorar si el caso aparece en la práctica.
- **Si la operación tampoco vuelve en 30 s tras la cancelación** (un controlador que no atiende la cancelación), se registra, el hilo bloqueado se abandona y la ejecución termina `Failed` con `Internal`. Se hace así para no quedarse colgada indefinidamente sin liberar la instantánea ni el bloqueo. Ver R12.
  - **Señal al `JobRunner`**: `SourceFileSystem` lanza `SourceOperationAbandonedException`, que deriva de `SourceReadingFailedException`. Esta **no** deriva de `IOException` ni de `UnauthorizedAccessException` (las únicas que el motor trata como error de un elemento suelto), así que atraviesa `BackupEngine` sin convertirse en un aviso, y el `JobRunner` la traduce a `Failed` con `Internal`. Desde ese momento, toda operación de ese `SourceFileSystem` la lanza.
  - Cuando el hilo abandonado por fin vuelve, cierra lo que haya abierto sin usarlo y no entrega ningún resultado.
- **Tope de hilos abandonados en todo el servicio** (M-1, decisión del coordinador). Se cuentan los hilos abandonados que aún no han vuelto, de cualquier ejecución y también de la resolución controlada (validación, `SaveJobAsync`, inicio de cada ejecución, cálculo de `PD`; §8.3). Es **un solo contador** para la lectura y la validación, incluida la repetición de la validación que hace el `JobRunner` al empezar cada ejecución (que no pasa por el límite de 4 validaciones simultáneas, §8.3; revisión final de HU-07, B-3, para HU-14): lo que se agota es el mismo recurso, hilos de SYSTEM colgados en un controlador. Una **lectura asíncrona** abandonada (no ha vuelto 30 s después de `CancelIoEx`) cuenta igual, como un hilo abandonado más, **hasta que vuelve**: no ocupa un hilo, pero retiene el handle, el búfer (B-3) y la petición pendiente en el controlador (cierre de HU-08 servicio, decisión del coordinador). Con **4** o más:
  - Las ejecuciones nuevas terminan `Failed` con `Internal` en el paso 2 de §8.4, **sin resolver orígenes, conectar ni leer nada**, con un mensaje que pide reiniciar el servicio (y su evento 2002, como cualquier copia fallida).
  - `ValidateJobAsync` y `SaveJobAsync` fallan con `Internal` sin abrir nada.
  - Se registra el evento **1005** (§8.5) al llegar a 4, una vez; vuelve a registrarse solo si el número baja de 4 y vuelve a llegar.
  - Motivo: cada hilo abandonado retiene una pila, un handle y quizá una instantánea pendiente de liberar en el controlador; un filtro que no atiende la cancelación no se arregla sin reiniciar. Reiniciar el servicio termina el proceso y con él esos hilos.

**Token de lectura de los orígenes (ADR-21; revisión del `SourceFileSystem` de HU-08, decisión del coordinador).** `FILE_OPEN_FOR_BACKUP_INTENT` solo salta la DACL si el token tiene `SeBackupPrivilege` **activado**, y LocalSystem lo tiene pero desactivado. Se activa así:

- **Solo en una copia, nunca en el token del proceso**. Al arrancar, el servicio abre su token de proceso, lo duplica con `DuplicateTokenEx` (`TokenImpersonation`, `SecurityImpersonation`) y, sobre la copia y con `AdjustTokenPrivileges`:
  - **quita** (`SE_PRIVILEGE_REMOVED`, irreversible) `SeRestorePrivilege`, `SeTakeOwnershipPrivilege`, `SeSecurityPrivilege`, `SeDebugPrivilege` y `SeImpersonatePrivilege`. Se quitan de uno en uno: quitar uno que el token no tiene (p. ej. porque el instalador ya lo ha excluido, §10) devuelve `ERROR_NOT_ALL_ASSIGNED` y no es un fallo;
  - **activa** solo `SeBackupPrivilege`;
  - comprueba con `GetTokenInformation(TokenPrivileges)` que la copia no tiene ninguno de los cinco y tiene `SeBackupPrivilege` activado.
- **Solo en los hilos dedicados de lectura**: los que hacen las aperturas y enumeraciones de `SourceFileSystem` y los de la resolución controlada de ADR-20 (§8.3), en la validación y al repetirla al ejecutar, para que validación y ejecución vean lo mismo. Reglas de esos hilos (recomendaciones de la revisión final de HU-07, aplicables al hilo de lectura y al de validación):
  - Se crean para eso con `new Thread(…)` y se arrancan con **`UnsafeStart`**, que no captura el `ExecutionContext`: así no viaja a ellos ninguna suplantación ni otro estado por `AsyncLocal` desde el hilo que los pide (por ejemplo, el de una llamada RPC).
  - El token es **siempre la copia del token del proceso** (arriba), asignada con `SetThreadToken` al empezar el hilo; **nunca** el token del cliente IPC ni una copia de él. Así `\??\` se resuelve en el espacio de nombres global de SYSTEM y no en el `DosDevices` de la sesión de un usuario, donde este podría haber definido sus propias letras. No se usa `WindowsIdentity.RunImpersonated` (restaura y propaga la identidad por el `ExecutionContext`, justo lo que se quiere evitar).
  - **Solo** ejecutan trabajos de lectura de una cola propia, y cada trabajo es **síncrono** (sin `await` dentro del hilo): ni hilos del *pool* ni continuaciones `async` (los resultados se entregan con `TaskCompletionSource` y `RunContinuationsAsynchronously`).
  - Al terminar el hilo (fin de la ejecución o de la validación) se llama a `RevertToSelf` y se cierra su referencia al token.
  - Un hilo **abandonado** (arriba, "Plazo") **conserva el token** hasta que vuelve o termina el proceso. Es aceptable porque no ejecuta nada más: cuando vuelve, solo cierra lo que haya abierto, llama a `RevertToSelf` y termina.

  Las lecturas asíncronas de contenido no necesitan el token (el acceso se comprueba al abrir) y pueden emitirse desde cualquier hilo.
- **Solo lectura**: todas las aperturas de esos hilos pasan por una única función que comprueba, **antes** de llamar a `NtCreateFile`, que el acceso pedido es un subconjunto de `GENERIC_READ | FILE_LIST_DIRECTORY | FILE_READ_ATTRIBUTES | SYNCHRONIZE` (con bits literales: nunca `MAXIMUM_ALLOWED`, `GENERIC_ALL`, `ACCESS_SYSTEM_SECURITY`, `DELETE`, `WRITE_DAC`, `WRITE_OWNER` ni nada de escritura), que la disposición es `FILE_OPEN` y que las opciones no incluyen `FILE_DELETE_ON_CLOSE` ni `FILE_OPEN_BY_FILE_ID`. Además (función `SourceOpen`, cierre de HU-08 servicio):
  - Una apertura **sin** `RootDirectory` (ruta absoluta) solo admite estas formas: `\??\X:\` (raíz de una letra), `\??\Volume{guid}\` (GUID de 36 caracteres entre llaves) y `\Device\HarddiskVolume<n>\` o `\Device\HarddiskVolumeShadowCopy<n>\` (`<n>` con la regla de "Raíces de dispositivo", arriba), siempre la raíz y nada detrás. Cualquier otra ruta absoluta se rechaza. Todo lo demás se abre relativo a un handle, con un solo componente.
  - Exige `FILE_OPEN_REPARSE_POINT` en todas las aperturas salvo en la **reapertura con nombre vacío** sobre el propio handle (segundo handle de la lista blanca, "Apertura para leer el contenido"), que es la única que lo omite.

  Si no se cumple, lanza `InvalidOperationException` (error de programación; la ejecución termina `Failed` con `Internal`) sin abrir nada. Hay prueba unitaria de esa función.
- **Nunca para escribir**: la restauración (§8.6, que abre con el token del usuario) y los almacenes de la carpeta de datos (ADR-14) no se ejecutan nunca en esos hilos, ni ningún otro código que escriba.
  - **Registro a archivo** (informativo, para quien implemente el registrador de `logs\`, RNF-12): esos hilos registran con `ILogger` como cualquier otro, así que el registrador a archivo **no puede escribir desde el hilo que llama**. Encola la entrada y la escribe desde un hilo o tarea propios, que nunca llevan el token de lectura. Si no, el archivo de log se abriría o escribiría con `SeBackupPrivilege` activado y en un hilo que puede quedar abandonado.
- **Si algo falla** al preparar la copia (duplicar, quitar, activar o la comprobación final), se descarta, se registra un aviso en el log y los hilos leen con el token del proceso **sin activar nada**: los archivos que SYSTEM no puede leer por su DACL darán `AccessDenied` como hasta ahora.
- **Lo que no cambia**: la protección de la carpeta de datos sigue siendo por ruta, antes de abrir (exclusión obligatoria en el motor) y después (ruta final), ADR-16 y ADR-18; los archivos cifrados con EFS siguen dando `ReadError` (el privilegio no descifra; leerlos exigiría `ReadEncryptedFileRaw`, fuera de alcance).
- **Enlaces duros**: el privilegio haría legible un enlace duro hacia `credentials\*.bin` creado dentro de un origen, y la ruta final no lo detecta (es uno de los nombres del archivo). La defensa es que un usuario estándar no puede crearlo (PM-HU08-01, paso 8).

### 8.3 Rutas

```
%ProgramData%\Backbone\
├── config\jobs.json, settings.json
├── credentials\<hash-del-recurso>.bin
├── data\history.db
└── logs\backbone-YYYYMMDD.log
```

`<hash-del-recurso>` es el SHA-256, en hexadecimal en minúsculas, de los bytes UTF-8 de la **raíz del recurso normalizada** (`\\servidor\recurso` en minúsculas, la que calcula `UncPaths.TryParse`, §7.5 A-3): una credencial por recurso, no por servidor (RF-60).

**La carpeta de datos nunca se copia (ADR-16, revisión de seguridad de HU-04).** Con DPAPI de ámbito equipo y entropía conocida, los archivos de `credentials\` solo están protegidos por su ACL local; si llegaran al NAS, cualquier usuario local con lectura en el recurso podría descifrarlos en este equipo. Dos capas:

**Carpetas protegidas** en esta sección: la carpeta de datos `%ProgramData%\Backbone` y las carpetas apartadas `Backbone.untrusted-<guid>` que haya junto a ella (ADR-13), que pueden contener credenciales antiguas cifradas igual. Sea `PD` la ruta final de `%ProgramData%`, obtenida con la misma resolución controlada que los orígenes ("Resolución controlada de los orígenes", abajo; ADR-20). Solo un administrador puede cambiarla, pero así ningún código del servicio deja que el sistema siga un enlace al abrir una ruta.

- **La carpeta de datos** es `PD\Backbone`; la comprobación del arranque garantiza que es una carpeta real, no un punto de reanálisis.
- **Una carpeta apartada** es una entrada de `PD` cuyo nombre empiece por `Backbone.untrusted-` (ordinal, sin distinguir mayúsculas), tenga o no un GUID válido detrás, **y que sea una carpeta real** (revisión de seguridad final de HU-13, M-B). `%ProgramData%` permite a cualquier usuario crear entradas, así que el servicio enumera `PD` por handle y abre cada entrada con ese prefijo con `CreateFile` y `FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_BACKUP_SEMANTICS`; sobre ese handle (`FileAttributeTagInfo`), una entrada que sea punto de reanálisis o archivo **se ignora**: ADR-13 solo aparta carpetas reales (el arranque rechaza, no aparta, una raíz que sea *junction* o archivo), y el motor ya no sigue un *junction* (RF-06). Si no se hiciera así, un usuario sin privilegios podría crear `C:\ProgramData\Backbone.untrusted-x` como *junction* hacia `C:\Users\alice\Documentos` y sacar esa carpeta de la copia sin aviso, o hacer que se rechazara un origen legítimo.
- **La ubicación manda, no el destino**: la ruta de una carpeta protegida es siempre `PD\<nombre>`; nunca se resuelve ni se sigue. En una ruta final (que ya no contiene puntos de reanálisis) basta, por tanto, con mirar el segmento que sigue a `PD`: `Backbone` o un nombre con el prefijo.
- **Como mucho 100 carpetas apartadas**. La búsqueda **deja de abrir entradas** en cuanto ha encontrado 101 carpetas reales: con eso ya sabe que hay demasiadas y no necesita contarlas todas (revisión de seguridad de HU-07, MEDIA-1). Si hay más entradas que cumplen lo anterior, el servicio registra un aviso en el log con el número y **falla cerrado** con los orígenes que contienen `PD` (los únicos que necesitan la lista para la capa 2): la validación los rechaza con `SourceNotAllowed` (`Value` = `PD`) y la ejecución termina `Failed` con `ValidationFailed`, con un mensaje que pide revisar las carpetas `Backbone.untrusted-*` de `%ProgramData%`. No se recorta la lista, porque entonces quien creara 100 carpetas con nombres que se ordenan antes dejaría fuera de la exclusión una carpeta apartada real con credenciales. Los orígenes que no contienen `PD` no se ven afectados. Es una denegación de servicio que puede provocar un usuario local (R11, §13).
- **`PD` desconocida** (cierre de HU-08 servicio, decisión del coordinador): si no se obtiene la ruta final de `%ProgramData%` en la forma `VOLUME_NAME_GUID` (falla la resolución controlada o `GetFinalPathNameByHandle` con `VOLUME_NAME_GUID`), el servicio no sabe en qué volumen están las carpetas protegidas y no puede decidir qué origen las contiene (I-5, punto 2). Registra un aviso en el log y la clasificación (`Classify`) **falla cerrado con todos los orígenes**, contengan o no `%ProgramData%` (`ProtectedFoldersUnknown`): la validación los rechaza con **`ProtectedFoldersUnavailable`** (30, contrato 1.4, §7.5; no con `SourceNotAllowed`) y la ejecución termina `Failed` con `ValidationFailed`. Lo mismo, para ese origen, si la ruta `VOLUME_NAME_GUID` de **un origen** viene vacía. A diferencia del caso anterior, no lo arregla revisar `Backbone.untrusted-*`: es un fallo del sistema o del volumen. Por eso tiene código y mensaje propios (§7.4: pide reintentar y, si se repite, revisar el log del servicio; R16, decidido).
- La lista se calcula de nuevo en cada validación y al empezar cada ejecución (una carpeta apartada puede aparecer en cualquier arranque).

1. **Validación de orígenes** (RF-03, `ValidateJobAsync`, `SaveJobAsync`): el servicio normaliza la ruta (§7.5 "Ruta de origen") y la resuelve con la **resolución controlada** (abajo, ADR-20), que nunca deja que el sistema siga un punto de reanálisis y no abre ningún destino que no sea un volumen local. Obtiene así la ruta final, con `GetFinalPathNameByHandle` (`FILE_NAME_NORMALIZED`) sobre el handle de la carpeta resuelta. Si la ruta final del origen es igual a la de una carpeta protegida o está dentro de ella (comparación ordinal sin distinguir mayúsculas, por segmentos completos, de las dos rutas finales en la forma `VOLUME_NAME_GUID`, como en el punto 2; como la ruta final no contiene puntos de reanálisis, equivale a que empiece por `PD\Backbone` o por `PD\` más un nombre con el prefijo de una carpeta real), el origen se rechaza con `SourceNotAllowed`. Al empezar cada ejecución, el `JobRunner` repite la comprobación **con la misma resolución controlada** sobre la ruta normalizada guardada en `jobs.json` (un origen puede haberse sustituido por un *junction* después de guardarlo; §8.4, paso 2):
   - Con `SourcePathInvalid`, `SourceNotLocal`, `SourceNotNtfs` o `SourceNotAllowed`, la ejecución termina `Failed` con `ValidationFailed` sin leer nada.
   - Con `SourceNotFound` o `SourceUnreadable`, ese origen se trata como raíz ilegible: aviso `SourceRootUnreadable` y se conserva del padre (§8.4 "Memoria del motor"). Los demás orígenes se copian.
2. **Exclusión obligatoria en el motor** (RF-04): si una carpeta protegida (`PD\<nombre>`) está dentro de la ruta final de un origen (p. ej. `C:\` o `C:\ProgramData`), el servicio calcula su ruta relativa a ese origen (`ProgramData\Backbone`, `ProgramData\Backbone.untrusted-<guid>`) y se la pasa al motor como exclusión obligatoria, aparte de los patrones del trabajo. El motor no entra en esas carpetas: no las recorre, no registra avisos por su contenido y no las incluye en el snapshot. Como la ruta es relativa al origen, vale igual al leer desde la instantánea VSS. No es un patrón *glob* de la lista de exclusiones y no se puede quitar. `ValidateJobAsync` lo indica con el aviso `SourceContainsDataFolder` y la app lo muestra como nota fija en la sección Exclusiones del editor (§9.2); no genera avisos de ejecución, para que una copia de `C:\` no termine siempre "con avisos" (RF-25). El formato del repositorio (§6) no cambia: lo excluido simplemente no aparece en `entries`.
   - **Por la identidad del volumen, no por la letra** (revisión del `SourceFileSystem` de HU-08, I-5): la resolución controlada admite orígenes cuya ruta final está en un volumen sin letra o al que se llega por `\??\Volume{guid}\…` (ADR-20), así que "la carpeta protegida está dentro del origen" se decide comparando las dos rutas finales en la **misma forma**: `GetFinalPathNameByHandle` con `VOLUME_NAME_GUID` (`\\?\Volume{guid}\…`) sobre el handle de la carpeta final del origen y sobre el de `PD`, por segmentos y sin distinguir mayúsculas. Nunca se compara la letra de una ruta con el GUID de otra ni se deduce el volumen de la ruta configurada. La ruta relativa que se pasa al motor sale de esa comparación.

La restauración tampoco puede escribir en esa carpeta (§8.6, punto 4).

**Resolución controlada de los orígenes (ADR-20; revisión de seguridad de HU-07, ALTA-1; decisión del coordinador).** Sustituye a la apertura "siguiendo los puntos de reanálisis" que había antes en el punto 1. Abrir siguiendo enlaces deja que SYSTEM resuelva dentro de `CreateFile` un enlace plantado en **cualquier** componente de la ruta: un enlace simbólico de carpeta hacia `\\atacante\r`, o un *junction* hacia `\RPC Control` más un enlace del administrador de objetos hacia `\??\UNC\…`, que un usuario sin privilegios puede crear. El equipo se autenticaría entonces ante el atacante con NTLM de su cuenta, contra §7.5 A-3 ("nunca se usa la cuenta del equipo"). La ruta final se comprobaba después y llegaba tarde. La resolución controlada la usan `ValidateJobAsync`, `SaveJobAsync`, el `JobRunner` al empezar cada ejecución y el cálculo de `PD`:

1. **Punto de partida**: la ruta normalizada `X:\seg1\…\segN` (§7.5). **Antes**, como filtro previo que no abre nada, `GetDriveType` de la letra: lo que no sea `DRIVE_FIXED` (unidades de red, `\Device\Mup`, extraíbles…) da `SourceNotLocal` sin abrir la raíz (revisión final de HU-07, B-2). **Después**, se abre la raíz del volumen (`\??\X:\`) con `NtCreateFile` y se comprueba **sobre ese handle**, que es lo que vale (la letra puede cambiar entre las dos cosas):
   - que es un disco local: `FileFsDeviceInformation` con `DeviceType` = `FILE_DEVICE_DISK`, sin `FILE_REMOTE_DEVICE` y sin `FILE_REMOVABLE_MEDIA`. Si no, `SourceNotLocal`;
   - que es la **raíz de un volumen** (revisión final de HU-07, B-1): `GetFinalPathNameByHandle` con `VOLUME_NAME_GUID` tiene que ser exactamente `\\?\Volume{guid}\`, sin ningún componente detrás. Si no (p. ej. una letra global definida con `subst` o `DefineDosDevice` hacia una subcarpeta), `SourceNotLocal`.
2. **Cada componente** se abre **relativo al handle del padre**: `NtCreateFile` con `OBJECT_ATTRIBUTES.RootDirectory` = handle del padre, `ObjectName` = **un solo** componente y `OBJ_CASE_INSENSITIVE`. Las opciones son `FILE_OPEN`, `FILE_OPEN_REPARSE_POINT`, `FILE_OPEN_FOR_BACKUP_INTENT` (los equivalentes de `FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_BACKUP_SEMANTICS`) y `FILE_COMPLETE_IF_OPLOCKED` (§8.2 "Plazo"), con el SQOS de identificación de §8.2 ("Apertura relativa") y el token de ADR-21, con acceso `FILE_READ_ATTRIBUTES | SYNCHRONIZE`, compartición de lectura y escritura y **sin `FILE_SHARE_DELETE`**. El handle del padre se mantiene abierto hasta abrir el hijo. Sobre el handle de cada componente se lee `FileAttributeTagInfo`.
   - **Por qué así y no de otra forma** (Microsoft Learn, [NtCreateFile](https://learn.microsoft.com/windows/win32/api/winternl/nf-winternl-ntcreatefile)):
     - Con `RootDirectory`, `ObjectName` es relativo a esa carpeta ya abierta. Al ser un solo componente, no queda ninguno intermedio que el sistema pueda volver a resolver por nombre.
     - Con `FILE_OPEN_REPARSE_POINT` "no se produce el procesamiento normal del punto de reanálisis" y se abre el propio punto de reanálisis, del que se puede leer el destino.
     - `OBJ_DONT_REPARSE` ([OBJECT_ATTRIBUTES](https://learn.microsoft.com/windows/win32/api/ntdef/ns-ntdef-_object_attributes)) hace fallar la apertura con `STATUS_REPARSE_POINT_ENCOUNTERED` sin devolver handle. Serviría para detectar el enlace, pero no para leer su destino sobre el mismo objeto, y su uso con `RootDirectory` en modo usuario no está documentado de forma expresa. No se usa como mecanismo principal.
     - `CreateFile` con la ruta completa y `FILE_FLAG_OPEN_REPARSE_POINT` solo protege el **último** componente. Abrir prefijos crecientes por ruta completa vuelve a resolver por nombre en cada apertura los componentes ya comprobados (TOCTOU).
3. **Clasificación de cada componente** (como en ADR-19, §8.2 "Clasificación por etiqueta"):
   - **Sin punto de reanálisis**, o de la **lista blanca** con contenido local (carpeta de nube totalmente poblada, WOF, Dedup): si es una carpeta, se sigue con el siguiente componente relativo a él. Si es un archivo, `SourceNotFound`.
   - **Sustituto de nombre** (`IsReparseTagNameSurrogate`: `IO_REPARSE_TAG_MOUNT_POINT`, `IO_REPARSE_TAG_SYMLINK` u otro con el bit N): su destino se lee con `FSCTL_GET_REPARSE_POINT` **sobre ese mismo handle**. Para *junction* y punto de montaje es el `SubstituteName` de `MountPointReparseBuffer`. Para un enlace simbólico es el de `SymbolicLinkReparseBuffer`, con `SYMLINK_FLAG_RELATIVE` si es relativo. Un sustituto de nombre de otra etiqueta, cuyo destino no se sabe interpretar, da `SourceNotLocal`.
     - **Destino admitido**, y solo este: un volumen local. `\??\X:\…` (letra de unidad) o `\??\Volume{guid}\…`, con el GUID entre llaves en el formato de 36 caracteres. Para un enlace relativo, el destino se compone **léxicamente** con la carpeta que contiene el enlace (`..` sube un componente). Si sube por encima de la raíz del volumen, se rechaza.
     - **Cualquier otro destino** da `SourceNotLocal` **sin abrirlo**: `\??\UNC\…`, `\Device\…` (incluido `\Device\Mup`), `\RPC Control\…`, `\GLOBALROOT\…`, `\??\GLOBALROOT\…`, `\\?\…`, `\??\` seguido de algo que no sea letra de unidad o volumen, rutas con `:` fuera de la letra, y destinos vacíos o mal formados. El destino se registra en el log con `UntrustedText.Describe`.
     - **Continuación**: la ruta pendiente pasa a ser destino + componentes que quedaban. Se vuelve al paso 1 con el volumen del destino: se abre su raíz, se comprueba que es un disco local y se recorre otra vez componente a componente. Nunca se pasa el destino al sistema como ruta completa para que lo resuelva.
   - **Solo en la nube**, carpeta de nube no poblada o **no legible** (otra etiqueta sin bit N): no se atraviesa ni se abre nada debajo, para no despertar a un proveedor ajeno ni bajar metadatos de la red. Da `SourceUnreadable`.
4. **Tope de saltos**: como mucho **63** sustitutos de nombre por resolución, el mismo límite que impone el sistema a una ruta ([Reparse points](https://learn.microsoft.com/windows/win32/fileio/reparse-points)). Al superarlo, `SourceUnreadable`. Un ciclo de enlaces termina así. Además (revisión final de HU-07, B-4):
   - la ruta compuesta (destino + componentes pendientes) **no puede superar 32 767 caracteres** en ningún momento; si los supera, `SourceUnreadable` sin abrir nada más;
   - como mucho **2 048 aperturas** en total por resolución, contando las raíces de volumen y todos los componentes de todos los saltos. Una ruta legítima no se acerca (32 767 caracteres dan, como mucho, unos 16 000 componentes de un carácter, y nadie configura así un origen), y el tope acota lo que un enlace hostil puede hacer recorrer a SYSTEM: 63 saltos que vuelven a componer rutas largas. Al superarlo, `SourceUnreadable`;
   - las operaciones lentas de la resolución (más de 10 s) suman como en el presupuesto de §8.2 "Plazo": con 10 min acumulados, `SourceUnreadable`. Un solo plazo vencido ya da `SourceUnreadable` ("Sin bloquear el hilo RPC", abajo).
5. **Defensa en profundidad**: sobre el handle de la carpeta final se obtiene `GetFinalPathNameByHandle` (`FILE_NAME_NORMALIZED`, `VOLUME_NAME_DOS` y `VOLUME_NAME_GUID`). Tiene que ser una ruta local y coincidir, por segmentos y sin distinguir mayúsculas, con la que ha compuesto la resolución. Si es UNC, da `SourceNotLocal`; si es otra cosa distinta, `SourceUnreadable`. Sobre ese mismo handle se leen el sistema de archivos (`GetVolumeInformationByHandle`, `SourceNotNtfs` si no es NTFS) y se hacen las comprobaciones de carpetas protegidas.
6. **Resultado**: la ruta final de la carpeta (la que se compara con las carpetas protegidas y de la que sale `ReadPath` en VSS, §8.2) y su volumen. Los handles se cierran al terminar, salvo que el llamador pida quedarse con el de la carpeta final. En una ejecución en vivo, `SourceFileSystem` **no recibe** ese handle: vuelve a bajar desde la raíz del volumen hasta esta ruta final, componente a componente y sin seguir ningún enlace (un enlace aparecido después de la resolución da `SourceRootUnreadable`), y compara con ella (ADR-18, §8.2 "Apertura relativa", cierre de HU-08 servicio); nunca la abre por ruta completa. **Requisito para HU-14**: el `JobRunner` pasa como `ReadPath` de cada origen en vivo la ruta final de esta resolución (`FinalPath`, o `GuidPath` si el volumen no tiene letra), **nunca la ruta configurada**; si pasara la configurada, un *junction* legítimo en ella daría `SourceRootUnreadable` en cada copia.
7. **Errores de apertura**: `STATUS_OBJECT_NAME_NOT_FOUND` y `STATUS_OBJECT_PATH_NOT_FOUND` dan `SourceNotFound`; acceso denegado y cualquier otro error, `SourceUnreadable`.

**Sin bloquear el hilo RPC (revisión de seguridad de HU-07, MEDIA-1).** La validación de orígenes no se hace de forma síncrona en el hilo que atiende la llamada RPC:

- Se ejecuta en un hilo de trabajo dedicado con el token de lectura de ADR-21 (§8.2 "Token de lectura de los orígenes"), con el `CancellationToken` de la llamada, que se cancela si se cierra la conexión.
- **Como mucho 4 validaciones de orígenes simultáneas en todo el servicio**. Cuentan `ValidateJobAsync`, `SaveJobAsync` y el cálculo de carpetas protegidas que hacen. Las demás esperan turno con el `CancellationToken` de su llamada. Con 4 basta para el uso interactivo (una app, alguna validación mientras se escribe) y se acota lo que una cuenta autorizada puede tener abierto como SYSTEM. Ya estaban acotadas las peticiones por conexión (16) y las conexiones (8, 4 por SID).
- El `JobRunner` **no** pasa por ese límite: una ejecución programada no espera a las validaciones de la app. Su resolución sí sigue el plazo de abajo.
- **Plazo**: cada apertura y cada `FSCTL_GET_REPARSE_POINT` tienen el plazo de §8.2 ("Plazo de las lecturas de los orígenes"): 60 s, con `CancelSynchronousIo`, y 30 s más para la cancelación. Al vencer, el origen da `SourceUnreadable`. Si la cancelación tampoco vuelve, el hilo se abandona y su plaza sigue ocupada hasta que vuelva. Así un filtro que no responde ocupa como mucho las 4 plazas y bloquea las validaciones, no el servicio (R12). Esos hilos cuentan además para el tope de hilos abandonados de todo el servicio (§8.2 "Plazo"): con 4, las ejecuciones nuevas y las validaciones fallan con `Internal` y se registra el evento 1005.
- La búsqueda de carpetas apartadas para en la 101 (arriba).

**Redirection Guard (decisión: se adopta como defensa complementaria).** Al arrancar, antes de leer ningún origen, el servicio llama a `SetProcessMitigationPolicy(ProcessRedirectionTrustPolicy)` con `EnforceRedirectionTrust = 1` ([PROCESS_MITIGATION_REDIRECTION_TRUST_POLICY](https://learn.microsoft.com/windows/win32/api/winnt/ns-winnt-process-mitigation-redirection-trust-policy)). El proceso deja entonces de seguir *junctions* creados por usuarios no administradores y el sistema registra el intento.

- **No sustituye a la resolución controlada**. Solo cubre *junctions*: no impide seguir enlaces simbólicos (que un usuario puede crear con el modo de desarrollador) ni los enlaces del administrador de objetos, y no está garantizado en todas las versiones de Windows 11 que admite Backbone.
- **Si la llamada falla** (versión que no lo admite u otro error), se registra un aviso en el log y el servicio sigue. La protección principal no depende de ella.
- **No rompe** ADR-13, ADR-14, ADR-18 ni ADR-19, que nunca siguen un punto de reanálisis. La resolución controlada tampoco, porque abre los enlaces con `FILE_OPEN_REPARSE_POINT` y los "sigue" ella misma.
- **Perfiles de usuario**: los *junctions* de compatibilidad (`Datos de programa`, `Mis documentos`…) los crea el sistema y no se ven afectados. Además, la copia no los sigue (RF-06).
- **Lo único que cambia** son las aperturas que el sistema resolvía siguiendo un *junction* creado por un usuario. En la práctica son las rutas de destino de una restauración (§8.6) o de una exportación del diagnóstico (§8.7) que pasen por un *junction* de usuario: fallan con `RestoreTargetNotWritable` o `TargetPathNotAllowed`, y el usuario tiene que elegir la ruta real. Se acepta, porque son justo las redirecciones que C-2 quiere evitar.
- Se comprueba en una prueba manual de HU-07 (con un *junction* creado por un usuario estándar y con los del perfil), que añade backbone-service.

**Comprobación de la carpeta de datos al arrancar (RNF-07, HT-03 I-1, ADR-13).** Antes de leer `settings.json` ni ninguna otra configuración, el servicio comprueba la raíz `%ProgramData%\Backbone` y su contenido:

- **Todo sobre handles**: cada objeto se abre con `CreateFile` y `FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT` (nunca se sigue un enlace); los atributos se leen con `GetFileInformationByHandleEx` (`FileAttributeTagInfo`) y la seguridad con `GetSecurityInfo`/`SetSecurityInfo` sobre ese handle, no sobre la ruta. La raíz y cada carpeta que se recorre se mantienen abiertas sin `FILE_SHARE_DELETE` mientras se tratan sus hijos, para que nadie pueda renombrarlas ni sustituirlas por un enlace a mitad.
- **Raíz inexistente**: se crea de forma atómica con `CreateDirectoryW` pasando el descriptor definitivo (propietario Administradores, DACL protegida de RNF-07), de modo que nunca existe con otra ACL. Si otro la crea entre medias (`ERROR_ALREADY_EXISTS`), se vuelve a evaluar lo que haya, con un número acotado de intentos (3).
- **Raíz que es punto de reanálisis o no es una carpeta**: se rechaza; nunca se toca el destino.
- **Raíz de propietario no fiable** (ni `S-1-5-18` ni `S-1-5-32-544`) **o que no se puede abrir** (acceso denegado): **nunca se corrige en el sitio**. Se aparta renombrándola por handle (`SetFileInformationByHandle`, `FileRenameInfo`, sin reemplazar) a `Backbone.untrusted-<guid>` en la misma carpeta, sin borrar nada, y se crea una nueva como en el caso de raíz inexistente. Si no se puede apartar (p. ej. hay handles abiertos que impiden abrirla con `DELETE`), el servicio **no arranca**.
- **Raíz de propietario fiable con DACL distinta de la canónica**: se aplica la DACL canónica en el sitio, por handle (riesgo aceptado R9, §13; los almacenes rechazan después lo que no tenga propietario fiable, §8.2).
- **Contenido**: ningún punto de reanálisis y todo con propietario SYSTEM o Administradores (si no, se rechaza: el servicio no arranca). Se acepta en cada **carpeta** solo **(a)** herencia sin ACE explícitas **y con todas las ACE efectivas de permiso y solo para SYSTEM o Administradores** (una ACE marcada a mano como heredada que conceda a otro SID, o una ACE de denegación, no basta), y en cada **archivo** **(a)** o **(b)** exactamente la DACL protegida canónica de RNF-07 (solo SYSTEM y Administradores, control total, sin herencia), que es la que tienen los archivos creados por la escritura atómica (§8.2). Las carpetas del contenido heredan siempre de la raíz. Cualquier otra DACL (ACE explícitas añadidas, herencia cortada con otras ACE, ACE "heredadas" que no cumplen lo anterior) se corrige: se quitan las ACE explícitas y se restablece la herencia, con lo que las ACE heredadas se recalculan desde la raíz. Como máximo 100 000 entradas.
- **Subcarpetas fijas**: después de comprobar el contenido y con la raíz todavía abierta, el servicio crea **las que falten** de `config\`, `credentials\`, `data\` y `logs\`, por handle (creación exclusiva de carpeta, que falla si ya existe una entrada con ese nombre, sin seguir enlaces) y **sin descriptor explícito**, para que hereden la DACL ya corregida de la raíz; sobre el handle de creación se comprueba que es una carpeta, no es un punto de reanálisis y tiene propietario fiable. Si el nombre ya existe, se ha tratado como contenido en el punto anterior (un *junction* o una entrada de propietario no fiable con ese nombre se rechaza: el servicio no arranca). Es el único sitio donde se crean carpetas: los almacenes no las crean (§8.2).
- **Resultado**:
  - Segura: nada que registrar.
  - Corregida (creada o con la DACL corregida): aviso en el log.
  - **Apartada y sustituida** (`Replaced`): aviso en el log y evento **1003** (§8.5), porque la configuración, el historial y las credenciales anteriores dejan de usarse y un administrador debe revisar la carpeta apartada.
  - Rechazada o una corrección que falla: el servicio no arranca, registra el evento **1002** (§8.5) y el SCM aplica la recuperación.

Crear la raíz con Administradores como propietario exige que el proceso pueda asignarlo (SYSTEM o un administrador elevado). El servicio lo hace **sin `SeRestorePrivilege`**, que no está entre sus privilegios (§10): el grupo Administradores del token de SYSTEM se puede asignar como propietario. Lo comprueba la prueba de aceptación de HU-01.

### 8.4 Ciclo de una ejecución

1. Comprobar condiciones (RF-13). Si no se cumplen → ejecución `Skipped` con motivo, se reintenta en el siguiente punto de programación.
2. Repetir la validación antes de conectar ni leer nada (revisión de seguridad de HU-07, BAJA-2):
   - **Orígenes**: resolución controlada y carpetas protegidas sobre las rutas normalizadas de `jobs.json` (§8.3 punto 1, ADR-20).
   - **Credencial**: tiene que haber una guardada para la raíz del recurso del destino. Si no la hay (p. ej. se borró después de guardar el trabajo), la ejecución termina `Failed` con `CredentialRequired` **sin intentar conectar**, porque nunca se usa la cuenta del equipo (§7.5 A-3). La ejecución usa la credencial guardada que lee en este paso.
3. Conectar con el recurso (`ShareConnectionManager`, §8.2); inicializar o validar el repositorio (RF-63).
4. Adquirir bloqueo `shared`.
5. Crear instantáneas VSS de los volúmenes de origen (RF-22).
6. Recorrer orígenes aplicando exclusiones (incluida la exclusión obligatoria de las carpetas protegidas, §8.3); comparar con el snapshot padre (RF-23, §6.3 "Snapshot padre"); subir objetos nuevos (§6.4).
7. Escribir el snapshot.
8. Aplicar retención (F2).
9. Liberar bloqueo, eliminar instantáneas, desconectar el recurso, restaurar el estado de energía (siempre, en `finally`).
10. Guardar en historial, escribir en el Visor de eventos, emitir `RunCompleted`.

Estados de ejecución: `Queued`, `Running`, `Completed`, `CompletedWithWarnings`, `Failed`, `Cancelled`, `Skipped`.

Fallos del motor y su código en `RunRecord.ErrorCode` (la ejecución termina `Failed` y no se publica snapshot): `RepositoryErrorKind.SnapshotTooLarge` → `SnapshotTooLarge`; `Corrupt` (también un snapshot padre o una cabecera dañados, ADR-17) → `RepositoryCorrupt`; el resto según la tabla de `RepositoryErrorKind` de Core (§7.4).

**Memoria del motor (RNF-05, revisión de seguridad de HU-13, MEDIA-1).** Lo que el motor acumula en memoria se acota **por bytes**, no solo por número, porque cada elemento puede llegar a decenas de KB (rutas de 32 767 caracteres):

- **Avisos**: se retienen como mucho 10 000 y mientras la suma de los tamaños en UTF-8 de sus textos (`path`, `code`, `message`, ya recortados a sus límites de §6.3) no supere el presupuesto de avisos de la cabecera (16 MiB − 256 KiB). El escritor serializa con escapes, que solo pueden agrandar el texto, así que el motor nunca descarta un aviso que el escritor habría guardado. Los que no caben solo se cuentan, para el resumen `WarningsTruncated`.
- **Listados**: el motor guarda la lista de hijos de cada carpeta que está recorriendo (para tratarlos en orden ordinal). La suma de lo que ocupan todas las listas abiertas a la vez se estima como 2 bytes por carácter de `Name` y `FullPath` más 64 bytes por elemento, con un presupuesto de **128 MiB**. Si al enumerar una carpeta se supera, se deja de enumerar, se descarta su lista y la carpeta se trata como **ilegible** (aviso `ReadError` que indica que tiene demasiados elementos; se conserva lo que había debajo en el snapshot padre, RF-25). Nunca se pierde en silencio una carpeta ni se supera el presupuesto.
- **Raíz de un origen ilegible** (revisión de seguridad final de HU-13, B-1; contrato 1.2): si lo que no se puede recorrer es la **raíz** de un origen, por exceder el presupuesto de listado o por cualquier otro error (sin permiso, error de lectura, o que se haya convertido en un enlace, en un marcador solo en la nube o en un punto de reanálisis no legible (ADR-19), o su ruta final no sea la esperada después de la comprobación de §8.3), el aviso es `SourceRootUnreadable` en lugar del código de la causa, con `path` = alias del origen y la causa en `message`. Todo el origen conserva lo que tenía en el snapshot padre y no se actualiza nada de él; la ejecución termina `CompletedWithWarnings` como con cualquier otro aviso, pero la app lo destaca con un texto propio ("no se ha copiado nada nuevo del origen …"), porque no es un archivo suelto sino todo el origen. Ver R11 (§13). A diferencia de una carpeta interior que pasa a ser un enlace (que se omite sin conservar su versión anterior, RF-06), la raíz conserva lo del padre: su sustitución a mitad de ejecución es un ataque o una carrera, no un cambio del usuario en su contenido.
- Las incidencias que el servicio guarda en el historial o envía por IPC (`RunDetail.Issues`) las acota el propio servicio con su límite de mensaje (`BackboneIpc.MaxMessageBytes`); no forman parte de esta regla.

### 8.6 Restauración segura

El servicio corre como SYSTEM y podría escribir en cualquier sitio. Para que un usuario autorizado no pueda usar la restauración para escribir donde él mismo no puede, ni redirigirla con enlaces (C-2), **cada carpeta y archivo de destino se crea o se abre con el token del usuario y SYSTEM solo escribe a través de ese handle**:

1. **Validación de la petición**:
   - La carpeta de destino (o la ubicación original de cada origen) es una ruta local completamente cualificada (`Path.IsPathFullyQualified`, letra de unidad de un volumen local), no UNC ni `\\?\` o `\\.\`.
   - Las rutas del snapshot cumplen `SnapshotPaths` (§7.5).
   - Cada nombre que se va a crear es un segmento válido.
2. **Handles bajo suplantación**: para cada carpeta y cada archivo de destino, el servicio suplanta al cliente (`NamedPipeServerStream.RunAsClient`) **solo durante la apertura**, de forma síncrona y mínima:
   - Abre o crea el objeto con `CreateFile` (relativo al handle de la carpeta padre cuando sea posible) con `FILE_FLAG_OPEN_REPARSE_POINT` (y `FILE_FLAG_BACKUP_SEMANTICS` para carpetas).
   - Si el objeto abierto es un punto de reanálisis (*junction*, enlace simbólico, montaje), **no se sigue**: el elemento falla con `RestoreTargetNotWritable`.
   - Con Redirection Guard (§8.3, ADR-20), tampoco se sigue un *junction* creado por un usuario no administrador en un componente intermedio de la ruta de destino. La apertura falla y da `RestoreTargetNotWritable`.
   - Revierte la suplantación. SYSTEM escribe el contenido, la fecha y los atributos **por ese handle**.
3. **Antes de copiar nada**, el servicio abre así la carpeta raíz de destino. Si el usuario no puede crear en ella → `RestoreTargetNotWritable` y no se escribe nada.
4. **Defensa adicional**: la ruta final de cada carpeta abierta (`GetFinalPathNameByHandle`, no la ruta pedida) se compara con `%WINDIR%`, `%ProgramFiles%`, `%ProgramFiles(x86)%` y `%ProgramData%\Backbone`. Si está dentro de alguna → `RestoreTargetNotWritable`. Esta lista no sustituye a los puntos 2 y 3.
5. **Archivos completos o nada**: cada archivo se escribe en un temporal creado igual que en el punto 2 en la misma carpeta, se verifica su hash (RF-33) y se renombra por handle (`SetFileInformationByHandle`, bajo suplantación) al nombre final según la política de conflicto. Un hash erróneo borra el temporal y marca el archivo como fallido.
6. Los objetos creados con el token del usuario tienen a ese usuario como propietario y heredan las ACL de la carpeta de destino.
7. La restauración pertenece al SID que la inicia (§7.3).

### 8.7 Exportación segura del diagnóstico (F2)

El servicio (SYSTEM) no devuelve el ZIP por el canal: lo escribe en la ruta que el usuario elige en la app (`DiagnosticsExportRequest.TargetPath`). Se descarta enviar el contenido por IPC porque exigiría multiplexar flujos o trocear en mensajes y mantener estado de transferencia, y el tamaño superaría `BackboneIpc.MaxMessageBytes`. Escribir suplantando reutiliza el mecanismo de §8.6. Reglas (M-8):

1. **Ruta**:
   - Completamente cualificada (`Path.IsPathFullyQualified`) con letra de unidad de un volumen local fijo.
   - No UNC, ni `\\?\`, `\\.\` o `\??\`.
   - Cada segmento cumple las reglas de `SnapshotPaths.IsValidSegment`, en particular sin `:`, que abriría un flujo alternativo (ADS), sin nombres reservados aunque lleven extensión (`NUL.zip`) y sin puntos ni espacios finales.
   - La extensión es `.zip` sin distinguir mayúsculas y el archivo no existe.
   - Si no se cumple → `ValidationFailed` con `TargetPathNotAllowed`.
2. **Creación**: suplantando al cliente solo durante la llamada, de forma síncrona y mínima, el servicio crea el archivo con `CreateFile(CREATE_NEW, FILE_FLAG_OPEN_REPARSE_POINT)` y revierte la suplantación.
   - Si el usuario no puede crearlo → `AccessDenied`.
   - La ruta final de la carpeta padre (`GetFinalPathNameByHandle`) no puede estar en las carpetas protegidas de §8.6.4; si lo está, se cierra y borra el archivo y se responde `ValidationFailed` con `TargetPathNotAllowed`.
3. **Escritura**: SYSTEM genera el ZIP en memoria o en `%ProgramData%\Backbone` y lo escribe **por el handle**; nunca vuelve a abrir la ruta por nombre.
4. **Contenido** (HU-23): configuración sin credenciales, logs de 14 días, últimas 100 ejecuciones y versiones. Nunca contraseñas ni el contenido de `credentials\` (RNF-06).
